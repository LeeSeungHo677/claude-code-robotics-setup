증상을 받아 **아래 계층부터 순서대로 배제**한다. 증상만 보고 상위 계층(플래너, 알고리즘)부터
의심하지 않는다 — 대부분 아래에서 끝난다.

인자로 증상을 받는다. 없으면 사용자에게 무엇이 이상한지 먼저 묻는다.

## 배제 순서

### L0. 프로세스가 살아 있는가
```bash
ros2 node list
ros2 node info /<node>
```
- 기대한 노드가 전부 떠 있는가. 죽은 노드가 있는가
- 죽었다면 왜 — journald/launch 로그 확인

### L1. 데이터가 흐르는가
```bash
ros2 topic list
ros2 topic hz <topic>      # 실제 주기
ros2 topic echo <topic> --once
```
- 토픽이 존재하는가, 발행되는가, 주기가 기대값인가
- **주기가 불안정하면** 그 노드의 CPU/블로킹 문제다 (`robot-perf-engineer` 참고)

### L2. QoS 가 맞는가
- 발행은 되는데 수신이 안 되면 거의 항상 QoS 불일치다. 에러 없이 조용히 실패한다
- `ros2 topic info <topic> --verbose` 로 양쪽 QoS 확인
- `~/.claude/skills/ros2-engineering/scripts/qos_checker.py` 활용

### L3. 시간이 맞는가
- `use_sim_time` 이 전 노드에서 일관된가
- 헤더 타임스탬프가 취득 시각인가, `now()` 인가
- 센서 간 타임스탬프 오프셋이 있는가
- `ros2 topic delay <topic>` 로 발행~수신 지연 확인

### L4. TF 가 연결되는가
```bash
ros2 run tf2_tools view_frames
ros2 run tf2_ros tf2_echo <parent> <child>
```
- 트리가 끊기지 않는가, 프레임을 두 곳에서 발행하지 않는가
- 변환이 최신인가 (오래된 변환은 lookup 실패)

### L5. 좌표계·단위가 맞는가
- 값의 크기가 물리적으로 말이 되는가 (m 인데 mm 값이 들어오지 않는가)
- 부호가 맞는가 (전진 명령에 후진하지 않는가)
- rad/deg 혼용이 없는가

### L6. 캘리브레이션
- 포인트클라우드를 이미지에 투영해 겹치는가
- 정지 시 위치가 흐르지 않는가 (IMU 바이어스)

### L7. 그 다음에 알고리즘

## 증상별 빠른 경로

| 증상 | 먼저 볼 곳 |
|---|---|
| RViz 에 아무것도 안 보임 | Fixed Frame → TF → 토픽 존재 → **QoS** |
| 로봇이 안 움직임 | `/cmd_vel` 발행 여부 → velocity_smoother/collision_monitor → 드라이버 → E-stop 상태 |
| 위치가 튐 | 정상일 수 있음(map→odom 보정). 제어가 map 프레임을 직접 쓰는지 확인 |
| 회전할 때만 이상 | 디스큐, IMU 외부 파라미터, 시간 동기화 |
| 가끔만 이상 | 타이밍/경합 — 주기 편차, 콜백 그룹, 로깅·GC |
| 시간이 지나면 느려짐 | 메모리 누수, 로그 누적, 그래프 무한 증가 |
| 실기에서만 실패 | 지연·CPU·열 — 시뮬에 없는 것들 |

## 원칙

- **한 번에 하나씩** 확인하고 결과를 기록한다.
- 확인한 것과 확인하지 못한 것을 구분해서 보고한다. 추측을 사실처럼 쓰지 않는다.
- 재현되는 증상이면 **rosbag 으로 기록**하게 한다. 기록 없는 현상은 분석할 수 없다.
- 진단 중 실기를 구동하는 명령은 실행하지 않는다. 조회 명령만 쓴다.
