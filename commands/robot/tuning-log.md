로봇 튜닝은 기록하지 않으면 **같은 실험을 반복하게 된다.**
이 커맨드는 튜닝 이력을 구조화해 남기고 이전 시도와 비교한다.

## 동작

1. 대상 파라미터 파일과 현재 값을 읽는다 (Nav2 params, 컨트롤러 YAML, SLAM 설정 등).
2. 튜닝 로그 파일을 찾거나 만든다 — 프로젝트 안 `docs/tuning/<대상>.md`.
   프로젝트 규약이 있으면 그것을 따른다.
3. 이번 변경을 항목으로 추가한다.
4. 이전 항목들과 비교해 **이미 시도한 조합인지** 알려준다.

## 기록 형식

```markdown
## 2026-08-15 14:30 — 좁은 통로 통과 실패 개선

**대상**: nav2_params.yaml / local_costmap.inflation_layer
**환경**: 로봇 D1 / 창고 B동 / 실기
**재현**: bags/2026-08-15_narrow_corridor.mcap

| 파라미터 | 이전 | 이후 | 이유 |
|---|---|---|---|
| inflation_radius | 0.55 | 0.35 | 통로 반폭 0.45m 보다 커서 전 구간이 치명 비용 |
| cost_scaling_factor | 3.0 | 3.0 | 유지 |

**결과**: 10회 중 9회 통과 (이전 0회). 다만 벽까지 거리가 12cm 로 줄어듦.
**부작용**: 코너에서 벽에 더 가까이 붙음. 속도를 0.6→0.5 로 낮춰 보완 필요할 수 있음.
**다음**: cost_scaling_factor 를 4.0 으로 올려 벽 근접을 완화할지 시험
**커밋**: abc1234
```

## 원칙 — 이걸 지키지 않으면 기록이 무의미하다

- **한 번에 하나씩 바꾼다.** 여러 개를 동시에 바꾸면 무엇이 효과였는지 영원히 모른다.
  여러 개를 바꿔야 한다면 그 사실을 기록에 명시한다.
- **재현 조건을 함께 남긴다** — 같은 rosbag, 같은 시작 위치, 같은 환경.
  조건이 다르면 비교가 아니다.
- **결과를 숫자로 적는다.** "좋아졌다" 가 아니라 "10회 중 9회 통과".
  1회 성공은 근거가 아니다.
- **부작용을 반드시 적는다.** 한 지표를 올리면 대개 다른 지표가 내려간다.
  적어두지 않으면 나중에 왜 되돌렸는지 모른다.
- 파라미터의 **물리적 의미와 단위**를 안 상태에서 바꾼다.
  값이 무엇을 뜻하는지 말할 수 없으면 바꾸지 않는다.

## 비교 요청 시

이전 기록들을 읽어 표로 정리한다:
- 어떤 파라미터가 몇 번 시도됐고 어떤 방향이 효과가 있었는지
- 아직 시도하지 않은 조합
- 서로 모순되는 결과가 있으면 지적한다 (조건이 달랐을 가능성)
