# 원격 조작 · 원격 지원

현장 AMR·서비스 로봇에서 **가동률을 실제로 결정하는 기능**이다.
로봇이 한 번 갇혔을 때 사람이 가야 하면 그 시간이 전부 다운타임이다.

이 문서는 세 부분이다: **개요·방식 선택** → **제어 구현** → **시스템·운영**.
관련 스킬: 서보/궤적은 `motion-planning`, 힘 제어·임피던스는 `manipulation-control`,
실시간 루프 제약은 `ros2-control`, 실기 구동 안전은 `robot-safety-compliance`.

## 세 가지를 구분한다 — 요구사항이 완전히 다르다

| | 직접 조작 | 공유 자율 | 원격 지원 |
|---|---|---|---|
| 무엇 | 사람이 속도 명령을 직접 | 사람이 방향 힌트, 로봇이 회피 | 사람이 **목표·판단**만 제공 |
| 지연 요구 | **엄격** (<100ms 급) | 중간 | 느슨 (초 단위 가능) |
| 대역폭 | 높음 (연속 영상) | 중간 | 낮음 (스냅샷이면 충분) |
| 위험 | 높음 | 중간 | 낮음 |
| 현장 권장 | 최후 수단 | 상황에 따라 | **기본으로 삼는다** |

**원격 지원을 기본 설계로 잡는다.** "로봇이 막혔다 → 사람이 사진 보고 우회 경로나
목표를 지정 → 로봇이 자율로 수행" 구조가 지연·대역폭·안전 모두에서 유리하다.
직접 조작은 그것으로 안 될 때만 쓴다.

## 지연 — 설계의 중심

- **영상 지연과 명령 지연을 따로 잰다.** 사람이 보는 화면이 300ms 과거인데
  명령은 즉시 나가면 조작자는 계속 과조작(overshoot)한다.
- 왕복 지연이 크면 **속도를 강제로 제한**한다. 지연 × 속도 = 사람이 못 보는 거리다.
  지연이 커지면 자동으로 감속하는 로직을 넣는다.
- 지연을 **화면에 표시**한다. 조작자가 모르면 판단할 수 없다.
- 예측 표시(로봇의 현재 추정 위치를 영상 위에 오버레이)가 체감 지연을 크게 줄인다.

## 영상 스트리밍

| 방식 | 특징 |
|---|---|
| **WebRTC** | 저지연, NAT 통과, 브라우저 지원. 원격 조작의 사실상 표준 |
| RTSP | 카메라 네이티브, 지연은 중간 |
| ROS `compressed` 이미지 브리지 | 구현이 쉽지만 지연·대역폭이 불리. 지원 용도로는 충분 |

- **원본 이미지 토픽을 무선/WAN 으로 보내지 않는다.** 압축은 필수.
- 해상도·프레임률을 **대역폭에 따라 동적으로** 낮춘다. 고정값으로 두면
  네트워크가 나빠질 때 지연이 무한히 쌓인다.
- 지연 누적(버퍼링)보다 **프레임 드롭**을 선택한다. 오래된 프레임은 쓸모없다.
- 여러 카메라가 있으면 조작자가 필요한 것만 켜게 한다. 전부 스트리밍하면 대역폭이 죽는다.

# 제어 구현

## 입력 → 명령 매핑

조이스틱 축을 그대로 속도에 곱하는 코드가 가장 흔한 시작점이자 가장 흔한 문제다.

```
raw axis ─→ 데드존 ─→ 곡선(expo) ─→ 스케일 ─→ 레이트/저크 제한 ─→ 명령
```

- **데드존**: 스틱 중립의 미세 잡음을 0으로 만든다. 없으면 손을 떼도 로봇이 슬금슬금 움직인다.
  데드존 밖은 **0부터 다시 시작하도록 재정규화**한다. 안 하면 데드존 경계에서 값이 툭 튄다.
  ```
  if |x| < dz: 0
  else: sign(x) · (|x| − dz) / (1 − dz)
  ```
- **expo 곡선**: `y = a·x³ + (1−a)·x` 형태. 중앙 부근을 둔감하게 만들어 미세 조작을 쉽게 하고
  끝단에서는 최대 속도를 유지한다. 정밀 작업일수록 a 를 키운다.
- **스케일**: 모드별로 다르게 준다 (정밀/일반/고속). 조작자가 전환할 수 있어야 한다.
- **레이트·저크 제한**을 반드시 마지막에 건다. 조작자가 스틱을 확 꺾어도 로봇은 부드럽게 반응해야 한다.
  이게 없으면 기구 충격, 적재물 낙하, 카메라 흔들림이 생긴다.
- 입력 장치가 끊기면 **즉시 0**. 마지막 값을 유지하지 않는다.

## 좌표계 — 매니퓰레이터 텔레옵의 핵심

"오른쪽으로" 가 **누구 기준의 오른쪽인가.** 이걸 정하지 않으면 조작자가 계속 헷갈린다.

| 기준 프레임 | 언제 |
|---|---|
| **operator view (카메라)** | 조작자가 영상을 보며 조작할 때. **대부분 이게 정답** |
| tool / end-effector | 툴 축을 따라 밀어 넣기 등 국소 작업 |
| base / world | 절대 좌표 기준 이동이 필요할 때 |

- 카메라 기준으로 하려면 입력 twist 를 `camera_frame → base_frame` 으로 변환한다.
  **TF 로 매 주기 변환**해야 한다 (카메라가 손목에 달려 있으면 자세가 계속 바뀐다).
- 현재 어느 프레임 기준인지 **UI 에 표시**한다. 프레임 착각이 텔레옵 사고의 큰 비중이다.
- 회전 입력도 같은 프레임 규약을 따라야 한다. 병진만 변환하고 회전을 빼먹는 실수가 흔하다.

## 모바일 베이스

- 차동구동이면 `(v, ω)` 로 매핑한다. 조이스틱 X를 ω, Y를 v 로 두는 것이 직관적이다.
- **회전 중 병진 제한**: 제자리 회전과 주행을 동시에 최대로 주면 바퀴가 미끄러진다.
  `|v| + k·|ω| ≤ v_max` 같은 결합 제약을 건다.
- 후진 시 속도를 낮춘다. 후방 센서 커버리지가 대개 부족하다.
- **온보드 장애물 회피를 유지**한다. 원격 명령을 `cmd_vel_teleop` 으로 내보내고
  `collision_monitor`/속도 스무더를 거쳐 최종 `cmd_vel` 이 나가게 한다.
  조작자 명령이 안전 계층을 우회하면 안 된다.

## 매니퓰레이터 조그(jog) / 서보

관절 하나씩이 아니라 **작업공간에서 실시간으로 움직이는 것**이 텔레옵의 요구다.
계획-실행(plan-execute) 사이클로는 불가능하다 — 서보 제어가 필요하다.

- **MoveIt Servo** 가 표준 해법이다. Twist(또는 관절 조그) 명령을 받아
  IK 를 매 주기 풀어 관절 명령을 낸다.
- 서보가 반드시 해야 하는 것 (직접 구현한다면 전부 넣어야 한다):
  - **특이점 감속**: 자코비안 최소 특이값이 작아지면 속도를 스케일 다운한다.
    감속 없이 그대로 보내면 관절이 폭주한다. 임계 도달 시 정지.
  - **관절 한계 감속**: 한계에 가까워지면 그 방향 성분만 줄인다. 급정지가 아니라 감속.
  - **충돌 인지**: Planning Scene 과의 거리에 따라 감속·정지. 텔레옵이라고 충돌 검사를 끄지 않는다.
  - **명령 타임아웃**: 입력이 끊기면 감속 정지.
  - **저역통과 필터**: 조작 입력의 잡음이 관절 명령으로 그대로 가지 않게.
- 서보 주기를 컨트롤러 주기와 맞춘다. 서보 100~250 Hz, 하부 제어 1 kHz 급이 전형적이다.
- IK 실패 시 **이전 명령을 유지하지 말고 정지**한다.

## 지연 보상

지연은 없앨 수 없으니 **제어 구조로 흡수**한다.

- **속도 제한**: 왕복 지연이 커지면 자동으로 속도 상한을 낮춘다. 가장 단순하고 확실하다.
  `v_max = min(v_설정, 안전거리 / RTT)` 형태.
- **예측 표시**: 명령을 보낸 뒤 로봇이 갈 위치를 로컬 모델로 추정해 영상 위에 오버레이한다.
  실제 지연을 줄이지는 못하지만 조작자의 과조작을 크게 줄인다. **투자 대비 효과가 가장 좋다.**
- **모델 기반 예측(Smith predictor 계열)**: 로봇 모델로 응답을 예측해 피드백 루프의
  지연을 보상한다. 모델 오차에 민감하므로 모델이 신뢰할 만할 때만 쓴다.
- **이동 명령을 이벤트화**: 연속 속도 명령 대신 "여기까지 가라" 를 보내면 지연에 훨씬 강해진다.
  → 이것이 원격 지원 방식을 권하는 제어적 이유다.

## 양방향(햅틱) 텔레오퍼레이션

힘 피드백을 조작자에게 되돌리는 경우. **안정성이 최대 과제**다.

- 통신 지연이 있는 힘 반사 루프는 **쉽게 발진한다.** 지연이 수십 ms만 되어도 불안정해질 수 있다.
- 안정화 기법:
  - **Passivity 기반 설계** — 통신 채널을 수동적(passive)으로 만든다
  - **Wave variable 변환** — 고정 지연에 대해 수동성을 보장하는 고전적 방법
  - **Time-Domain Passivity Control (TDPC)** — 에너지를 실시간 감시해 필요할 때만 감쇠 주입.
    가변 지연에 유리
- 힘 스케일링을 둔다. 로봇이 받는 힘을 그대로 사람 손에 주면 위험하다.
- 햅틱 없이 **시각적 힘 표시**(바 그래프, 색)로 대체해도 실무에서 충분한 경우가 많다.
  햅틱 하드웨어를 도입하기 전에 이것부터 시도한다.

## 클러치 · 모션 스케일링

- **클러치(clutching)**: 마스터 장치가 작업 범위 끝에 닿으면 버튼을 눌러 연결을 끊고
  손을 되돌린 뒤 다시 연결한다. 마우스를 들었다 놓는 것과 같다.
  - 클러치 해제/재연결 시 **위치 점프가 없어야 한다.** 재연결 시점의 마스터 자세를
    새 기준점으로 잡는다. 이걸 안 하면 재연결 순간 로봇이 튄다 — 텔레옵의 대표적 사고.
- **모션 스케일링**: 마스터 이동 : 로봇 이동 = 1:0.2 처럼 축소하면 정밀 작업이 쉬워진다.
  확대는 넓은 범위 이동에. 조작 중 전환 가능하게 만든다.

## 공유 자율 (Shared Autonomy)

조작자 입력과 자율 시스템을 섞는다. 원격 지원 다음으로 실용적인 구조다.

- **Arbitration(중재) 규칙을 명시**한다:
  - 자율이 회피, 사람이 방향 — 가장 흔하고 안전한 조합
  - 사람 입력에 가중치를 두되 안전 제약은 자율이 절대 양보하지 않는다
  - 사람 입력이 없으면 자율이 계속 수행
- **가상 고정구(virtual fixture)**: 특정 평면·축·영역으로 움직임을 구속한다.
  "이 면을 따라서만" / "이 원기둥 안에서만". 삽입·연마 작업에서 성공률을 크게 올린다.
  구속을 임피던스로 구현하면(벽에 가까울수록 강한 반발) 부드럽게 느껴진다.
- 사람과 자율이 **서로 싸우지 않게** 한다. 자율이 회피하려는 방향과 사람이 미는 방향이
  반대면 로봇이 진동한다. 우선순위와 블렌딩 계수를 명시적으로 설계한다.

## 시연 데이터 수집으로 연결

텔레옵은 **모방학습의 데이터 수집 장치**이기도 하다 (`imitation-learning` 스킬).

- 수집을 염두에 두면 텔레옵 설계가 달라진다:
  - 조작 주기 = 정책 배포 시 제어 주기로 **맞춰서 기록**한다
  - 관측(카메라)과 액션(명령)의 **타임스탬프를 정렬**해 기록한다.
    어긋나면 정책이 미래를 보고 행동하는 것을 배운다
  - 필터·스케일링을 거친 **최종 명령**을 기록한다. 원시 조이스틱 값이 아니다
- 조작자의 망설임 구간은 나중에 걸러내야 하므로, **세션 중 구간 표시(마킹) 버튼**을 두면 좋다.

## 테스트

- **지연을 인위적으로 주입해 시험**한다. 랩 환경은 지연이 거의 없어 문제가 안 보인다.
  ```bash
  sudo tc qdisc add dev eth0 root netem delay 150ms 30ms loss 1%
  sudo tc qdisc del dev eth0 root          # 해제
  ```
  50/100/200/400 ms 에서 각각 조작해 보고 어느 지점부터 제어가 불가능해지는지 기록한다.
  그 값이 운영 시 속도 제한의 근거가 된다.
- 통신을 **완전히 끊어** 정지하는지 확인한다. 코드 리뷰로 대체하지 않는다.
- 클러치 재연결, 모드 전환, 인수인계 순간을 반복 시험한다. 사고는 전환에서 난다.
- 시뮬레이션에서 먼저 전 시나리오를 통과시킨다 (`gazebo` 스킬).

# 시스템 · 운영

## 안전 — 원격은 더 위험하다

조작자는 로봇 주변을 **직접 보지 못한다.** 이 전제로 설계한다.

- [ ] **데드맨 스위치**: 조작자가 계속 입력해야 움직인다. 놓으면 정지
- [ ] **명령 타임아웃**: 명령이 끊기면 즉시 정지 (마지막 명령 유지 금지)
- [ ] **로컬 안전이 원격보다 우선**: 원격 명령이 와도 온보드 장애물 감지가 이기게 한다.
      원격 조작 중이라고 안전 계층을 끄면 안 된다
- [ ] **속도 상한**을 자율 주행보다 낮게 건다
- [ ] **연결 끊김 시 동작 정의**: 즉시 정지가 기본
- [ ] 조작 권한 획득/반납이 **명시적**이어야 한다. 두 사람이 동시에 조작하면 안 된다
- [ ] 모든 원격 조작 세션을 **누가·언제·무엇을** 로깅한다 (사고 시 책임 소재)

## 인수인계 (자율 ↔ 수동 전환)

**전환 순간이 가장 위험하다.**

- 자율 → 수동: 진행 중이던 목표·궤적을 **명시적으로 취소**한다. 안 하면 조작 종료 후
  로봇이 예전 목표로 갑자기 출발한다.
- 수동 → 자율: 현재 위치에서 재계획한다. 이전 계획을 재개하지 않는다.
- 전환 시 **속도를 0 으로 만든 뒤** 넘긴다. 움직이는 상태로 권한을 넘기지 않는다.
- 조작자 UI 에 **현재 모드를 크게** 표시한다. 모드를 착각한 조작이 사고의 흔한 원인이다.

## 조작자 UI

- 지연, 연결 품질, 배터리, 현재 모드, 안전 상태를 **항상 보이게** 둔다.
- 로봇이 왜 멈췄는지(장애물? 로컬라이제이션? 작업 실패?) 원인을 표시한다.
  원인을 모르면 조작자가 잘못된 조치를 한다.
- 원격 지원이라면 **선택지를 제시**하는 UI 가 좋다 — "우회 경로 A/B", "이 물체 무시",
  "작업 취소". 자유 조작보다 안전하고 빠르다.
- 여러 로봇을 한 사람이 담당하면 **주의를 요하는 로봇으로 자동 전환**되게 한다.

## 확장 (플릿 규모)

- 조작자 1명이 로봇 N대를 담당하는 비율이 사업성을 결정한다.
  이 비율을 **지표로 측정**하고, 개입 유형별 빈도를 분석해 자동화 대상을 찾는다.
- 개입이 잦은 위치·상황을 지도에 누적하면 맵이나 알고리즘의 문제 지점이 드러난다
  (`robot-data-pipeline` 의 플라이휠).
- 원격 지원 요청 → 응답까지의 시간이 다운타임이다. 대기열과 우선순위를 설계한다.
