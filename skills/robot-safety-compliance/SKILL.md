# 기능 안전 · 규격

**소프트웨어만으로 안전을 만들 수 없다.** 이 스킬의 목적은 어디까지가 소프트웨어의 몫이고
어디부터가 하드웨어·규격의 몫인지 구분하는 것이다.

> 이 문서는 설계 방향을 잡기 위한 실무 정리이지 법적·인증적 판단이 아니다.
> 실제 인증은 해당 규격 원문과 인증기관·안전 엔지니어의 검토가 필요하다.
> 적용 규격은 로봇 종류·국가·용도에 따라 다르다.

## 규격 지형

| 규격 | 대상 |
|---|---|
| **ISO 12100** | 기계류 일반 — 위험성 평가와 저감의 기본 틀 |
| **ISO 10218-1/-2** | 산업용 로봇 (로봇 자체 / 시스템 통합) |
| **ISO/TS 15066** | 협동로봇 — 인체 접촉 시 힘·압력 한계 |
| **ISO 3691-4** | 무인운반차·AMR (산업용 트럭) |
| **ISO 13849-1** | 안전 관련 제어부 — Performance Level(PL a~e), Category |
| **IEC 61508 / 62061** | 전기·전자 기능안전 — SIL |
| **IEC 60204-1** | 기계 전기 장비 — 정지 카테고리 |

## 정지 카테고리 — 용어를 정확히 쓴다

| 카테고리 | 동작 |
|---|---|
| **Category 0** | 즉시 전원 차단. 제어되지 않은 정지 (관성으로 계속 움직일 수 있음) |
| **Category 1** | 제어된 감속 후 전원 차단 |
| **Category 2** | 제어된 정지, **전원은 유지** (구동은 살아 있음) |

- **Protective stop (보호 정지)** 과 **Emergency stop (비상 정지)** 는 다르다.
  비상정지는 사람이 누르는 것이고, 보호정지는 센서가 트리거하는 정상 운용의 일부다.
- 비상정지는 **하드웨어 배선**이어야 한다. 소프트웨어가 토픽을 받아 정지시키는 것은
  비상정지가 아니다. 소프트웨어가 죽으면 동작하지 않기 때문이다.
- **STO (Safe Torque Off)** 는 드라이브 레벨에서 토크를 제거하는 기능. 안전 회로가 여기에 연결된다.

## 안전 아키텍처 원칙

```
안전 회로 (하드웨어)  ─── E-stop 버튼, 안전 스캐너, 안전 릴레이/PLC → STO
        │  독립
소프트웨어 감시자     ─── 속도/영역/힘 감시, 이상 감지 → 감속·정지 요청
        │
일반 제어 스택        ─── Nav2, 컨트롤러, 계획
```

- **안전 계층은 일반 스택과 독립된 실행 경로**를 가져야 한다.
  플래너가 죽어도, 인지가 죽어도, 심지어 메인 컴퓨터가 죽어도 정지할 수 있어야 한다.
- 안전 관련 신호는 **이중화(dual-channel)** 와 **불일치 감지**를 요구하는 경우가 많다
  (ISO 13849 Category 3/4). 단일 배선 + 소프트웨어 판단은 낮은 PL 밖에 못 받는다.
- **Fail-safe 설계**: 신호가 끊기면 안전한 쪽(정지)으로 간다.
  E-stop 은 상시 닫힘(NC) 회로로 구성해 단선 시 정지되게 한다.
- 안전 기능의 **응답 시간**을 측정하고 문서화한다. "정지 명령 → 실제 정지"까지의
  최악 시간이 정지 거리를 결정한다.

## 위험성 평가 (반드시 먼저)

1. 사용 용도와 **오사용(foreseeable misuse)** 을 정의한다
2. 위험원 식별 — 충돌, 끼임, 낙하, 전기, 화재, 소음
3. 위험 추정 — 심각도 × 노출 빈도 × 회피 가능성
4. 위험 저감 (**순서가 중요**):
   a. 본질적 안전 설계 (속도·힘 제한, 모서리 라운딩, 질량 감소)
   b. 방호 장치 (안전 스캐너, 펜스, 라이트 커튼)
   c. 사용 정보 (경고, 매뉴얼, 교육)
5. 잔여 위험 문서화

**소프트웨어 안전 기능은 대부분 (b) 에 해당한다.** (a) 를 건너뛰고 소프트웨어로 메우려 하면
필요한 PL 이 올라가고 검증 비용이 폭증한다.

## 협동 로봇 (ISO/TS 15066)

사람과 공간을 공유할 때 네 가지 방식:
1. **안전 정격 감시 정지** — 사람이 들어오면 정지, 나가면 재개
2. **핸드 가이딩** — 사람이 직접 로봇을 잡고 유도
3. **속도·거리 감시** — 거리에 따라 속도를 줄임 (분리 거리 계산 필요)
4. **동력·힘 제한** — 접촉해도 인체 한계 이하 (신체 부위별 힘·압력 한계표 존재)

- 4번을 쓰려면 **실제 접촉 시험**으로 힘·압력을 측정해야 한다. 시뮬레이션 값으로 대체할 수 없다.
- 3번의 분리 거리는 로봇 정지 거리 + 사람 접근 속도 + 시스템 응답 시간으로 계산한다.
  응답 시간에 **인지 지연까지** 포함해야 한다.

## AMR / 모바일 로봇 (ISO 3691-4)

- 안전 스캐너(레이저)는 **안전 정격 제품**이어야 한다.
  일반 LiDAR 를 소프트웨어로 감시하는 것은 안전 기능으로 인정되지 않는다.
- 속도에 따라 보호 영역(protective field)을 전환한다. 빠를수록 넓게.
- 정지 거리 = 응답 시간 × 속도 + 제동 거리. 실측하고 여유를 둔다.
- 사각지대(측면, 후방, 낮은 장애물, 계단 하강)를 평가한다.
  2D 스캐너 하나로는 지게차 포크나 낮은 팔레트를 못 본다 — 실제 사고 유형이다.

## 조작 UI 의 위험도 표시

버튼·명령 목록처럼 **사람이 눌러서 로봇을 움직이는 UI** 에는 위험도가 보여야 한다.
아래는 실제 관제 대시보드를 만들며 같은 실수를 네 번 반복한 뒤 정리한 규칙이다.

### 판정은 이름이 아니라 결과로 한다
**"멈추는 것처럼 들리는 명령이 실제로는 로봇을 움직인다."** 가장 자주 틀리는 지점이다.

| 명령 | 직관 | 실제 |
|---|---|---|
| **팔 토크 OFF** | 끄는 것 = 안전 | **팔이 중력으로 처진다** → 구동 |
| **제어권 해제** | 놓는 것 = 안전 | **상위 제어기가 즉시 명령할 수 있다** → 구동 |
| 힘제어 모드 전환 | 설정 변경 | 거동이 바뀐다 → 조작 |
| 제자리 회전 | 이동 아님 | 본체가 움직인다 → 구동 |
| **정지** | — | 위험을 줄인다 → **조회** |

판정 질문은 하나다: **이 명령의 결과로 로봇이 물리적으로 움직일 수 있는가?**

### 등급과 마찰
| 등급 | 대상 | 마찰 |
|---|---|---|
| 조회 | 로봇 상태가 안 바뀜. **정지처럼 위험을 줄이는 것도 여기** | 없음 |
| 조작 | 물체·엔드이펙터만 움직임 | 없음 (색으로 표시만) |
| 구동 | 본체가 움직이거나 움직일 수 있는 상태가 됨 | **길게 누르기(약 600ms)** |
| 비상정지 | — | **마찰 0. 확인 대화상자 금지** |

- **위험을 줄이는 명령에 마찰을 두지 않는다.** 정지를 누르기 어렵게 만들면 안전 장치가 아니라 위험 요소다.
- 브라우저 `confirm()` 보다 **길게 누르기**가 낫다 — 빠르고, 오조작에 강하고, 리듬을 깨지 않는다.
- E-STOP 은 **어떤 모달이 떠 있어도** 같은 위치·같은 밝기·클릭 가능해야 한다 (오버레이 z-index 위로).

### 표시는 이중 인코딩
**색 단독으로 등급을 구분하지 않는다.** 색 + 텍스트 등급(또는 아이콘)을 함께 쓴다.
- 색맹 사용자에게 전달되지 않는다
- 밝은 테마에서 1px 테두리 색차는 구분되지 않는다 (실측으로 확인됨)
- 굵은 좌측 색 바(3px 이상) + 텍스트 라벨 조합이 안정적이다

### 잘못된 배지는 없는 것보다 나쁘다
배지가 없으면 사용자는 조심한다. **잘못된 배지는 안심시킨다.**
그리고 등급이 틀리면 그 등급에 걸린 마찰 보호까지 함께 우회된다.
→ 조작 UI 를 추가·수정할 때마다 **전체 명령의 등급을 다시 훑는다.** 한 개만 고치지 않는다.

### 여러 화면이 있으면 규칙을 공유한다
컨셉·화면마다 위험도 표현을 새로 만들면 제품 안에서 규칙이 갈린다.
**등급 정의와 마찰 규칙은 한 곳에 두고 모든 화면이 참조**한다.

## 소프트웨어가 해야 할 일

안전 회로와 별개로 소프트웨어에서 반드시 구현할 것:

- [ ] **워치독**: 각 핵심 노드의 하트비트 감시. 끊기면 감속·정지
- [ ] **명령 유효성 검사**: 속도·가속도·관절 한계를 초과하는 명령을 하드웨어로 보내지 않는다
- [ ] **명령 타임아웃**: 새 명령이 안 오면 정지한다. 마지막 명령을 유지하지 않는다
- [ ] **상태 일관성 검사**: 로컬라이제이션 신뢰도, 센서 생존, TF 유효성. 이상 시 자율 중단
- [ ] **모드 전환 안전성**: 수동↔자율 전환 시 잔여 명령이 실행되지 않게 정리
- [ ] **속도 제한**: 영역별·모드별 최대 속도를 코드가 아니라 설정으로 관리하고 강제
- [ ] **이벤트 로깅**: 모든 안전 이벤트를 시각과 함께 기록 (사고 분석의 유일한 근거)

## 검증

- 안전 기능은 **실제로 트리거해서 시험**한다. 코드 리뷰로 대체하지 않는다.
  E-stop 을 누르고 정지 거리를 자로 잰다.
- 시험 항목·조건·결과를 문서로 남긴다. 납품 시 요구된다.
- 안전 관련 코드는 변경 시마다 재시험한다. 회귀 시험 목록을 만들어 둔다.
- 안전 기능을 개발 편의로 끄는 경로를 만들지 않는다. 만들어야 한다면
  물리적으로 구분되게(개발용 하드웨어 키 등) 하고 현장 빌드에서 제거한다.

## 문서화 (납품·인증용)

- 위험성 평가서
- 안전 기능 목록과 각각의 PL/SIL 목표 및 근거
- 안전 회로도, 부품 안전 인증서(안전 릴레이, 스캐너)
- 응답 시간·정지 거리 측정 결과
- 시험 성적서
- 사용자 매뉴얼의 안전 섹션, 잔여 위험 경고

**이 문서들은 개발 후에 만드는 것이 아니라 개발과 함께 쌓는 것이다.**
나중에 몰아서 만들면 설계 근거를 재구성할 수 없어 인증이 지연된다.
