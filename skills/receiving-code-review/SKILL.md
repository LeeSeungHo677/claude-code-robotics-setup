# 리뷰 지적 반영

리뷰 지적은 **검토할 제안**이지 따라야 할 명령이 아니다. 검증하고, 모르면 묻고, 그다음 고친다.

## 절차

1. **전부 읽는다** — 반응하기 전에 끝까지.
2. **이해한다** — 각 항목을 자기 말로 다시 적는다. 못 하겠으면 그 항목은 질문이다.
3. **불명확한 항목이 하나라도 있으면 아무것도 고치지 않고 먼저 묻는다.**
   항목끼리 얽혀 있는 경우가 많다 — 1·2·3·6 만 이해했으면 "4·5 를 확인해야 시작할 수 있다" 고 말한다.
4. **코드베이스와 대조한다** — 이 코드베이스에서 기술적으로 맞는가? 기존 동작을 깨는가?
   지금 구현에 이유가 있는가(호환성·하드웨어 제약·과거 결정)? 리뷰어가 전체 맥락을 봤는가?
5. **반영 순서**: 막는 문제(빌드 깨짐·보안·안전) → 단순 수정(오타·import) → 복잡한 수정(로직·리팩터).
   **한 항목씩 고치고 그때마다 테스트한다.** 몰아서 고치면 어느 수정이 무엇을 깼는지 모른다.

## 반박할 때

- 제안이 기존 기능을 깨거나, 이 스택에서 틀렸거나, 쓰이지 않는 기능을 "제대로" 만들라는 것(YAGNI —
  `grep` 으로 실제 호출처를 확인)이면 **근거를 들어** 반박한다. 방어적으로가 아니라 사실로.
- 검증할 수 없으면 그렇게 말한다: "X 없이는 확인할 수 없습니다. 조사할까요, 그대로 갈까요?"
- 사용자가 이전에 내린 설계 결정과 충돌하면 고치지 말고 사용자와 먼저 상의한다.
- 반박했는데 틀렸으면: "확인해보니 맞습니다 — Y 때문에 제가 잘못 봤습니다. 고칩니다." 길게 사과하지 않는다.

## 로봇 코드에서 추가로

- **`robot-safety-reviewer` 의 안전 지적(E-stop, 워치독, 속도·힘 제한, 타임아웃)은 내 판단으로 기각하지 않는다.**
  틀렸다고 보이면 근거와 함께 사용자에게 올리고 결정을 받는다.
- 단위·좌표계·QoS 지적은 "맞는 것 같다" 로 넘기지 말고 실제 값(frame_id, rad/deg, QoS 프로파일)을 확인한 뒤 반영한다.
- 반영 후 하드웨어 동작이 바뀌는 수정이면 실기 검증 명령을 제시만 하고 사용자가 실행하게 한다 (전역 규칙).

## 말투

- 맞는 지적이면 "고쳤습니다 — [무엇을 어디서]" 만. "좋은 지적입니다!" 같은 인사치레는 쓰지 않는다 — 고친 코드가 답이다.
- GitHub 인라인 코멘트에는 그 스레드에 답한다 (`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`),
  PR 최상위 코멘트로 달지 않는다.

| 실수 | 대신 |
|---|---|
| 동의부터 하고 구현 | 요구를 다시 적고 코드와 대조 |
| 일부만 이해한 채 시작 | 불명확한 항목부터 질문 |
| 몰아서 고치고 한 번에 테스트 | 항목마다 테스트 |
| 리뷰어가 맞다고 가정 | 깨지는 것이 없는지 확인 |
| 검증 못 했는데 진행 | 한계를 말하고 방향을 묻는다 |
