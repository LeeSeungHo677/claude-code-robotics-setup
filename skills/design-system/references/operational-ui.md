## 꼭 지킬 것 — 안전 최소선 2개

관제 화면도 컨셉·레이아웃·색·분위기는 자유다(SKILL.md 3a). 어느 컨셉이든 아래 두 가지만은 빠지면 안 된다 —
디자인 취향이 아니라 사고를 막는 장치라서다. **생김새는 컨셉마다 자유, "있어야 한다" 만 고정.**

1. **실기 / 시뮬 / 재생 표시** — 실제 로봇을 움직이는 화면인지 한눈에 알 수 있게, 스크롤해도 사라지지 않게.
   어느 창이 실기에 명령을 보내는지 헷갈리면 실기 사고로 이어진다 (CLAUDE.md 「실기와 시뮬을 항상 구분」 의 화면판, 세부 예시 §5).
2. **알람·상태를 색만으로 구분하지 않는다** — 색에 모양·숫자·문구 중 하나 이상을 겹친다.
   흐린 화면·색맹·흑백 출력에서도 심각도가 읽혀야 한다 (예시 §1).

## 참고 자료 — 관제 화면 관례 (필수 아님)

아래는 산업 HMI·항공·관제에서 오래 써 온 관례와 근거다. 컨셉을 정할 때 **골라 쓰는 재료**이지 지켜야 할 규칙이 아니다.
요약하면 "정상은 조용히, 색과 움직임은 비정상에, 숫자는 맥락과 함께, 화면은 개요 → 문제 → 상세" 쪽이 판독에 유리하다는 경험칙이다.
다른 방향을 고른 컨셉이면 그 이유를 DESIGN.md 에 한 줄 남기면 된다.

## 1. 색 · 알람

| 규칙 | 왜 | 근거 |
|---|---|---|
| **정상 = 회색 또는 무표시.** 정상 로봇에 green 점을 찍지 않는다. 채도 있는 색은 알람·비정상·주의 필요에만 | 정상까지 색이 있으면 비정상 색이 묻힌다. 색이 드물어야 주변 시야에서 튄다 | [표준] ISA-101 단색 권장(2차 출처) · Few *Why Most Dashboards Fail* |
| **꺼짐 = 정상** 이 되게 한다(dark cockpit). 단 "꺼짐" 과 "신호 없음" 을 반드시 구분 (§3 stale) | 수백 개 상태를 훑지 않고 켜진 것만 보면 된다 | [관행] Airbus 설계 철학(2차 출처) |
| 등급마다 **색 + 모양 + 문구** 고정. 예: 1 = 빨간 사각형 "1", 2 = 노란 삼각형 "2" + "모터 1 과열" | 색맹·흐린 화면·흑백 출력에서도 읽힌다 | [관행] HP-HMI 벤더 · Astro status system |
| 묶음 상태는 **가장 높은 심각도로 올린다**(roll-up). 로봇 → 구역 → 사이트 | 개요 한 칸만 보고 어디로 내려갈지 안다. 평균 내면 숨는다 | [관행] Astro: "Use the highest level of urgency…" |
| 빨강은 "즉시 조치" 하나에만. off 와 emergency 를 같은 빨강으로 칠하지 않는다. 상태색 세트를 늘리지 않는다 | 남용하면 사용자가 빨강을 무시한다 | [관행] Astro 사용자 연구 |
| **깜빡임은 ack 안 된 알람에만**, ack 하면 즉시 정지. 값 갱신·정상에는 절대 | 가장 강한 신호를 한 뜻에 묶어 둔다 | [관행] ISA-101 해설(Tatsoft) |
| **알람 예산**: 정상 운영 중 운영자 1명당 10분에 1건 미만, 이상 발생 후 첫 10분 10건 미만. 우선순위 분포 high 5 · medium 15 · low 80 % 근처. 대시보드 자체 지표로 측정 | 숫자가 있어야 "이 알람은 빼자" 를 결정한다. 현장은 high 가 5~6배로 부풀기 쉽다 | [표준] EEMUA 191 (로봇 fleet 적합성 미검증 — 출발점) |

> `ui-ux-design` §3 의 "정상/성공 = green" 은 **폼 제출·작업 완료 같은 일회성 결과**에 쓴다.
> 상시 감시 화면의 정상 상태에는 이 표가 우선한다.

## 2. 숫자

- `font-variant-numeric: tabular-nums slashed-zero;` — 로봇 ID·시리얼·IP 처럼 O/0 혼동이 사고로 이어지는 곳에 slashed zero.
  폰트에 `zero` 대체 글자가 있는지 확인한다.
- 핵심 값에는 **맥락 3종**: ① 목표·한계 ② 정상 범위 ③ 최근 추세. "7,822 — compared to what?" (Few). 눈금 없는 게이지 금지.
- 연속값(배터리·모터 온도·위치 오차·지연)은 게이지 대신 **bullet graph / moving analog indicator** — 가로 막대 1줄에
  현재 값 마커 · 정상 범위(옅은 band) · 경고/위험 구간 · 목표선 · 정지(interlock) 한계. 세로로 쌓아 "막대 뱅크".
  약 2초에 "범위 밖인가 · 얼마나 · 한계까지 얼마" 를 훑는다 [관행: HP-HMI·Ignition, Few].
- 추세는 화살표(↑↓) 대신 **글자 높이 sparkline** — 축·격자·범례 없이 마지막 점과 min/max 만 (Tufte). 차트 세부는 번들 `dataviz`.

## 3. 실시간 · stale

- **값마다 나이(age)를 갖는다.** topic·필드별 stale timeout = 기대 주기 × 2~3.
- 지나면 값을 **흐리게·빗금**으로 두고 나이("12s") 표시. 마지막 값을 지우지 않되 정상처럼 보이지 않게.
  stale 표현은 알람색과 겹치지 않게 — 회색 + 빗금 / 점선 테두리 (업계 통일 규약은 없다, 우리 DESIGN.md 에 고정).
  빗금은 막대·칸 배경에만 — **글자 위에 겹치면 취소선처럼 읽힌다**(2026-11-26 A/B 시안 390 폭에서 실제 발생).
- **No data**(아무것도 안 옴) 와 **missing series**(일부만 끊김) 를 구분한다 (Grafana).
- 대기 표시: <100ms 아무것도 / 100ms~1s 시각 단서 / 1~10s 스피너 / 10s+ 진행률 / 1분+ "나가도 됨 + 완료 알림".
  더 많이 넣는 것보다 **빨리 뜨는 것**이 밀도를 높인다 (Ström, *UI Density*).

## 4. 레이아웃

- **화면 위계 4단계** [표준 ISA-101 §6.3, 세부 수치는 벤더 해석]:

  | 단계 | 담을 것 | 갱신 |
  |---|---|---|
  | L1 개요 | 사이트·구역 상태, 구역별 활성 알람 수. 편차만 | 1~2 s |
  | L2 운영 | 로봇 1대 / 작업 셀 하나의 조작 화면 | 0.5~1 s |
  | L3 상세 | 관절별 값, trend, faceplate | 필요 시 |
  | L4 지원 | 진단·설정·로그 | — |

  어느 화면이든 3클릭 안에. 한 화면에 단계를 섞으면 "지금 문제 있나" 를 판단할 수 없다.
- **fleet 첫 화면 = 로봇 1대 1행 밀집 표**, 카드 그리드 아님. 행 24~32px, 열: 상태 모양 · ID · 모드 · 배터리 bullet ·
  지연 sparkline · 마지막 메시지 나이 · 현재 작업. 정렬은 **심각도 우선**, 정상 행은 접는다 (Bloomberg·ATC strip 목록).
- **fleet 비교 = small multiples** — 같은 지표를 같은 축·같은 크기 작은 차트 격자로. 한 차트에 N개 선을 겹치지 않는다.
- **density 모드** 2~3단계: 행 24 / 32 / 40~48 (Carbon). 관제실 벽면·노트북·현장 태블릿(장갑)은 같은 화면이라도 밀도가 다르다.
- 길 찾기 크롬(사이드바·탭·헤더)은 본문보다 **대비를 한두 단계 낮춘다.** 작업 영역이 이긴다 (Linear 2026).

## 5. 로봇 특화

- **환경 배너 — 실기 / 시뮬 / 재생.** 화면 맨 위에 스크롤되지 않는 전체 폭 띠, 가능하면 아래에도. 문구 예:
  `REAL ROBOT · site-A` / `SIM` / `REPLAY 2026-11-20 14:03`. 환경마다 색 고정, **상태색과 다른 색**.
  어느 창이 실제 로봇을 움직이는지 헷갈리는 것이 큰 사고로 이어진다. (원리: 국방·정부 UI 의 classification banner —
  실기/시뮬 구분에 쓰는 것은 우리 응용. CLAUDE.md 「실기와 시뮬을 항상 구분」 의 UI 판)
- **teleop 은 영상과 지도를 하나의 장면으로.** 영상·지도(occupancy/costmap)·pose·거리센서를 한 2.5D/3D 장면에 겹친다.
  나란히 두면 운영자가 머릿속에서 좌표계를 맞춰야 한다 [연구: Nielsen·Goodrich·Ricks, IEEE T-RO 2007 — 통합 화면에서
  완료 시간·충돌·workload 감소. 매니퓰레이터 적용은 미검증].
- **영상 지연을 측정해서 상시 표시.** 프레임 timestamp 와 현재 시각 차(glass-to-glass)를 영상 위에. 한계를 넘으면 테두리
  색 변경·흐림. teleop 모드에서는 부드럽게 보이려고 버퍼를 늘리는 설정을 끈다. 0.5 s 지연만으로 원격 조종이 매우 어려워진다
  [연구 다수. 화면 표기 방식의 표준은 없다]. 제어 쪽은 `teleoperation` 스킬.
- **분석·재생 화면 = 공유 타임라인 + 비대칭 분할.** 3D/지도 2/3, 오른쪽에 카메라·plot 세로 스택. 모든 패널이 하나의 재생 시각,
  plot 에 현재 시각 세로선 (Foxglove 레이아웃).

## 6. 개성 — 판독을 해치지 않는 곳에서만

정체성을 줄 수 있는 곳은 세 군데다. 상태색·밀도·레이아웃 문법은 표준을 따른다.

1. **무채색의 온도** — 차가운/따뜻한 회색. Linear 는 파랑기 회색 → 따뜻한 회색으로 바꿨다.
2. **본문·숫자 폰트 짝**
3. **회사 고유 상징 하나** — Bloomberg 의 amber-on-black 처럼. 우리라면 로봇 glyph·지도 스타일·환경 배너

테마는 **base · accent · contrast 입력 3개에서 OKLCH 로 생성**한다(Linear: 변수 98개 → 3개). contrast 하나로 고대비 테마도 나온다.

> "회색 화면 + accent 하나" 가 **절제가 아니라 카테고리 기본값**으로 보일 때가 있다(impeccable Operate).
> 그럴 때 색을 늘리지 말고 위 1·2·3 으로 정체성을 준다.

## 7. 이미 쓰는 도구를 바꿀 때

위치·단축키·용어를 유지하고 **한 번에 한 축만** 바꾼다. 운영자를 설계에 참여시키고 왜 바꾸는지 설명한다.
구 레이아웃 토글을 한동안 둔다. 폰트 하나, 버튼 위치 하나도 숙련자 업무를 방해할 수 있다 (Bloomberg, ISA-101 해설, Linear).
