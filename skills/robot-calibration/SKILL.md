# 캘리브레이션 · 시간 동기화

인지·제어 버그의 상당수는 알고리즘이 아니라 **캘리브레이션과 타임스탬프**에서 나온다.
알고리즘을 고치기 전에 여기부터 배제한다.

## 순서가 중요하다

```
1. 시간 동기화   ← 이게 틀리면 아래 전부 무의미
2. 카메라 내부 파라미터 (intrinsic)
3. 센서 간 외부 파라미터 (extrinsic)
4. 로봇-센서 (hand-eye)
5. 오도메트리 / IMU 바이어스
```

각 단계는 앞 단계가 맞다는 전제 위에 서 있다. 순서를 건너뛰면 뒤 단계에서
"왜 안 맞지" 를 영원히 반복한다.

## 1. 시간 동기화

**가장 먼저, 가장 자주 놓치는 것.**

- 타임스탬프는 **데이터가 취득된 순간**이어야 한다. 콜백에서 `now()` 를 찍으면
  전송·처리 지연이 그대로 오차가 된다. 드라이버가 하드웨어 타임스탬프를 주는지 확인한다.
- 여러 컴퓨터에 센서가 붙어 있으면 **PTP(IEEE 1588)** 를 쓴다. NTP 는 밀리초 수준이라
  고속 주행·고속 조작에서는 부족하다. `phc2sys`, `ptp4l` 로 확인.
- 가능하면 **하드웨어 트리거**로 카메라·LiDAR 를 동기 발화시킨다. 소프트웨어 동기화는
  최후 수단이다.
- 동기화 검증: 움직이는 물체를 두 센서로 동시에 관측하고, 시간축을 밀어가며
  오차가 최소가 되는 오프셋을 찾는다. 그 오프셋이 0이 아니면 아직 안 맞은 것이다.
- ROS 2 에서는 `message_filters` 의 `ApproximateTime` 을 쓰되, **허용 슬롭을 명시**한다.
  슬롭을 크게 잡으면 동기화가 되는 것처럼 보이지만 실제로는 다른 시점의 데이터를 짝지은다.

진단:
```bash
ros2 topic delay /camera/image_raw     # 발행 시각 vs 헤더 시각 차이
ros2 topic hz /scan /camera/image_raw  # 주기 안정성
```

## 2. 카메라 내부 파라미터

- 체커보드/ChArUco 로 `camera_calibration` 또는 Kalibr 사용. ChArUco 가 부분 가림에 강하다.
- **재투영 오차(reprojection error)** 를 반드시 확인한다. 0.3 px 이하를 목표로,
  1 px 이 넘으면 다시 찍는다. 오차 수치를 안 보고 넘어가면 나중에 전부 무너진다.
- 이미지 **전 영역**을 덮도록 찍는다. 중앙만 찍으면 왜곡 계수가 엉뚱하게 추정된다.
  가장자리·모서리·기울인 자세를 반드시 포함한다.
- 왜곡 모델을 렌즈에 맞게 고른다. 광각/어안은 pinhole+radtan 으로 맞지 않는다 (equidistant/fisheye).
- 결과는 `camera_info` 토픽으로 발행되어야 한다. YAML 만 만들고 발행을 안 하면
  하류 노드가 못 쓴다.

## 3. 센서 간 외부 파라미터

### LiDAR ↔ 카메라
- 타깃 기반(체커보드/보드) 또는 무타깃(엣지·상호정보량) 방식.
  현장에서는 타깃 기반이 재현성이 좋다.
- 검증: 포인트클라우드를 이미지에 투영해서 **직선 구조물(문틀, 기둥)이 어긋나는지** 본다.
  숫자보다 눈이 빠르다. 어긋나면 회전(rotation)이 틀린 것이고,
  전체가 평행 이동해 있으면 병진(translation)이 틀린 것이다.
- 회전 오차 1°는 10 m 거리에서 약 17 cm 오차가 된다. 각도를 우습게 보지 않는다.

### IMU ↔ 카메라
- Kalibr 로 시간 오프셋까지 함께 추정한다. VIO/LIO 를 쓸 거면 필수.
- IMU 는 충분히 여러 축으로 흔들어야 관측 가능해진다. 정적인 데이터로는 추정되지 않는다.

## 4. Hand-Eye 캘리브레이션

로봇 팔과 카메라의 상대 자세를 구한다. **eye-in-hand**(카메라가 손목에) vs
**eye-to-hand**(카메라가 고정)를 먼저 명확히 한다 — 수식이 다르다.

- `AX = XB` 형태. Tsai-Lenz, Park, Daniilidis, Horaud 등. OpenCV `calibrateHandEye` 로 충분.
- **자세를 다양하게** 수집한다. 같은 평면에서만 움직이면 해가 축퇴(degenerate)된다.
  회전축을 서로 다르게, 최소 10~15 자세 이상.
- 로봇의 FK 가 정확하다는 전제가 있다. 관절 오프셋이 틀려 있으면 hand-eye 결과가
  그 오차를 흡수해버려서 특정 자세에서만 맞는다.
- 검증: 알려진 위치의 마커를 **여러 다른 로봇 자세에서** 관측해 월드 좌표가 일정한지 본다.
  한 자세에서만 맞으면 실패한 것이다.

## 5. 오도메트리 / IMU 바이어스

- 휠 오도메트리: 직진 캘리브레이션(휠 반경) → 회전 캘리브레이션(트레드 폭) 순서.
  UMBmark 같은 정사각 주행 테스트로 계통 오차를 분리한다.
- IMU 바이어스: 정지 상태에서 장시간 수집해 자이로/가속도 바이어스와 노이즈 밀도(Allan variance)를 구한다.
  이 값이 상태추정 필터의 노이즈 파라미터로 들어간다 — 추측값을 넣으면 필터가 발산한다.
- 온도에 따라 바이어스가 변한다. 로봇을 켜자마자와 30분 후가 다르다.
  현장 로봇이라면 워밍업 후 캘리브레이션한다.

## 캘리브레이션 결과 관리

- 결과는 **버전 관리**한다. 로봇 개체별로 다르므로 `robot_id` 와 캘리브레이션 날짜를 함께 저장한다.
- URDF 에 하드코딩하지 말고 별도 YAML 로 분리해 로드한다. 재캘리브레이션 시 URDF 를 안 건드려도 되게.
- **언제 다시 해야 하는가**: 센서를 물리적으로 만졌을 때, 충돌 후, 온도 환경이 크게 바뀐 후,
  그리고 정기적으로. "한 번 했으니 됐다" 는 현장에서 통하지 않는다.
- 재캘리브레이션 전후 성능을 같은 rosbag 으로 비교해 기록을 남긴다.

## 증상 → 의심 순서

| 증상 | 먼저 의심 |
|---|---|
| 포인트클라우드가 이미지와 안 겹침 | LiDAR-카메라 extrinsic, 그다음 시간 동기화 |
| 겹치는데 **움직일 때만** 어긋남 | 시간 동기화 (정적일 땐 안 보인다) |
| 팔이 일정한 offset 으로 빗나감 | hand-eye translation |
| 팔이 자세에 따라 다르게 빗나감 | hand-eye rotation 또는 FK/관절 오프셋 |
| 이미지 가장자리 물체 위치가 틀림 | 왜곡 계수 (중앙만으로 캘리브레이션함) |
| 로봇이 직진하는데 맵이 휘어짐 | 휠 오도메트리 트레드 폭, IMU 자이로 바이어스 |
