# 노트·문서 검토

기본 위치: **`~/Documents/Obsidian Vault`** (업무 노트 — 국책과제, 작업지시서,
기술지원 체크리스트, 로봇 내부기능 메모). 다른 경로를 주면 그쪽을 본다.

**요약해주는 것이 목적이 아니다.** 노트는 쓴 사람이 이미 안다.
여기서 하는 일은 **"지금도 맞는가, 빠진 게 뭔가"** 를 찾는 것이다.

## 무엇을 찾는가

| 찾을 것 | 어떻게 |
|---|---|
| **낡은 항목** | 날짜·버전·상태가 적힌 줄을 실제 코드·로봇·git 이력과 대조 |
| **모순** | 두 문서가 같은 대상을 다르게 적은 곳 (버전·수량·담당·일정) |
| **끝나지 않은 것** | 체크되지 않은 항목, "확인 필요", "TBD", 답 없는 질문 |
| **근거 없는 단정** | 측정치 없이 "된다/안 된다" 라고 적힌 것 |
| **후속이 안 잡힌 결론** | 결론은 있는데 누가 언제 무엇을 하는지가 없는 것 |

## 대조 대상 — 노트만 읽고 판단하지 않는다

노트가 틀렸는지 알려면 밖을 봐야 한다.

- **코드·git**: 작업지시서 항목이 이미 구현됐는지 `git log`·소스로 확인
- **로봇 문서**: `~/knowledge/robots/` 의 하드웨어·SDK 분석과 어긋나는지
- **실기 기록**: `docs/robot-sdk/g2-onsite-check-*.md` 같은 현장 확인 기록
- 노트가 맞고 코드가 낡았을 수도 있다. **어느 쪽이 최신인지 근거로 판정한다**

## 다룰 때 주의

- **원문을 함부로 고치지 않는다.** 사람이 손으로 쓴 업무 노트다.
  고칠 것이 있으면 **무엇을 왜 고칠지 먼저 보여주고** 동의를 받는다
- 고치게 되면 **원문을 지우지 말고 취소선이나 `~~` 로 남기고 날짜를 붙인다.**
  국책과제·기술지원 문서는 나중에 "그때 뭐라고 적었나" 가 필요해진다
- **개인정보·거래처명·단가**가 들어 있을 수 있다. 밖으로 내보내는 요약에는 넣지 않는다
- Obsidian 링크 문법 `[[...]]` 을 깨뜨리지 않는다. 파일명을 바꾸면 링크가 끊긴다
- 빈 파일(`무제.md` 같은 것)은 지우자고 하지 않는다. 쓰다 만 것일 수 있다

## 출력

```markdown
# 노트 검토 — <범위> (YYYY-MM-DD)

## 지금 조치가 필요한 것
| 문서 | 항목 | 왜 | 제안 |
|---|---|---|---|

## 낡았을 가능성
- (노트 내용 ↔ 실제 상태, 어느 쪽이 최신인지 근거와 함께)

## 모순
- (문서 A 와 B 가 어긋나는 지점)

## 미결
- (끝나지 않은 항목. 누가 무엇을 해야 닫히는지)
```

검토 결과를 vault 안에 남길지, 대화로만 볼지는 **물어보고 정한다.**
vault 는 사용자의 개인 작업 공간이다.

## Gotchas

- **읽지 않은 문서를 판단하지 않는다.** 범위가 넓으면 어디까지 읽었는지 명시한다
- "정리했습니다" 라고 말하기 전에 **무엇을 바꿨는지 파일별로 나열한다**
- 노트에 적힌 일정·담당은 사실이 아니라 **그 시점의 계획**이다. 현재형으로 단정하지 않는다
- 체크리스트 항목을 임의로 체크하지 않는다. 완료 판단은 사용자가 한다
