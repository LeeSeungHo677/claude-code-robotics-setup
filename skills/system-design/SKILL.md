# 시스템 설계 (서버 · 플랫폼)

로봇 온보드 아키텍처(`system-architecture`)와는 제약이 다르다.
여기서는 **여러 사용자·여러 로봇·시간이 지나도 유지되는 서버 시스템**을 다룬다.

## 0. 먼저 수치로 만든다

설계 전에 답해야 할 것. 답이 없으면 아직 설계할 단계가 아니다.

- 로봇/사용자 **수**와 1년 뒤 예상치
- 쓰기·읽기 **QPS**, 피크 대 평시 비율
- 데이터 **증가율** (텔레메트리는 초당 수 KB × 로봇 수 × 86400 → 금방 TB 가 된다)
- **지연 요구**: 사용자가 기다릴 수 있는 시간 (관제 화면 갱신 1초? 5초?)
- **가용성 요구**: 서버가 죽으면 로봇이 멈추는가, 계속 돌아가는가 ← 이게 설계를 바꾼다
- 보존 기간과 규제 요구

**대부분의 시스템은 생각보다 작다.** 단일 PostgreSQL + 앱 서버 2대로 충분한 것을
마이크로서비스로 쪼개면 비용만 늘고 디버깅이 불가능해진다.

## 1. 서비스 분할 — 나누는 데 비용이 든다

**모놀리스로 시작하는 것이 대부분 정답이다.** 나눌 근거가 생겼을 때 나눈다.

나눌 근거:
| 근거 | 설명 |
|---|---|
| **독립 배포 필요** | 이 부분만 하루에 여러 번 배포해야 한다 |
| **독립 확장 필요** | 이 부분만 CPU/메모리를 10배 쓴다 |
| **장애 격리 필요** | 이게 죽어도 나머지는 살아야 한다 |
| **팀 경계** | 다른 팀이 소유한다 |

**아닌 근거**: "코드가 커져서", "마이크로서비스가 요즘 표준이라서", "기능이 달라서".

나누면 생기는 비용: 네트워크 호출, 분산 트랜잭션, 버전 호환, 분산 추적,
로컬 개발 환경 복잡도. 이 비용을 감당할 이유가 있어야 한다.

경계를 그을 때는 **데이터 소유권**으로 자른다. 두 서비스가 같은 테이블을 쓰면
그건 나뉜 것이 아니라 결합이 숨겨진 것이다.

## 2. 데이터 저장 선택

| 데이터 | 저장소 |
|---|---|
| 관계·트랜잭션·정합성 | **PostgreSQL** — 기본값. 대부분 여기서 시작한다 |
| 캐시·세션·큐·랭킹 | Redis (`redis-patterns`) |
| **시계열 텔레메트리** | TimescaleDB / InfluxDB / Prometheus — 로봇 지표는 여기 |
| 대용량 파일 (rosbag, 영상, 모델) | 객체 저장소(S3 호환). **DB 에 넣지 않는다** |
| 전문 검색 | OpenSearch / PG full-text |
| 그래프 관계 | 대개 PG 로 충분. 진짜 그래프 질의가 필요할 때만 전용 DB |

- **로봇 텔레메트리를 일반 RDB 에 넣으면 몇 달 안에 터진다.** 시계열 저장소를 쓰거나
  파티셔닝 + 다운샘플링 + 보존 정책을 처음부터 설계한다.
- 원본은 객체 저장소, 메타데이터·인덱스만 DB — 이 분리가 표준이다.
- 스키마 설계: 정규화로 시작하고, 측정된 병목이 있을 때만 비정규화한다.
- **마이그레이션 전략**을 처음부터 정한다 (`alembic` 등). 무중단 마이그레이션은
  "추가 → 병행 쓰기 → 백필 → 전환 → 제거" 5단계다. 컬럼을 바로 바꾸지 않는다.

## 3. API 설계

- 계약 우선. 응답 형태를 전 서비스에서 통일한다 (`api-designer` 스킬).
- **버저닝**을 처음부터. `/v1` 없이 시작하면 나중에 넣을 수 없다.
- **멱등성**: 재시도 가능한 쓰기 API 는 `Idempotency-Key` 를 받는다.
  네트워크가 불안정한 로봇 클라이언트에서는 필수다.
- 페이지네이션은 커서 기반. 로봇 목록이 10개일 때 잘 되는 offset 이 10만 건에서 죽는다.
- **레이트 리밋**을 API 게이트웨이 레벨에서. 로봇 하나가 폭주해도 전체가 죽지 않게.
- 대량 조회는 배치 엔드포인트를 준다. 로봇 100대 상태를 100번 요청하게 하지 않는다.

## 4. 비동기 · 큐

동기로 처리하면 안 되는 것: 무거운 계산, 외부 API 호출, 대용량 처리, 재시도 필요한 작업.

- 큐 선택: **Redis 기반**(간단, 유실 가능) vs **RabbitMQ/NATS**(라우팅) vs
  **Kafka**(대용량 스트림·재생 필요). 로봇 텔레메트리 파이프라인이면 Kafka/NATS 급을 검토.
- **at-least-once 가 기본**이다 → 소비자는 **반드시 멱등**해야 한다.
  같은 메시지를 두 번 처리해도 결과가 같아야 한다.
- **Dead Letter Queue** 를 반드시 둔다. 실패한 메시지가 무한 재시도로 큐를 막는 것이
  가장 흔한 장애다.
- 재시도는 **지수 백오프 + 지터**. 동시에 재시도하면 서버가 다시 죽는다.
- 큐 깊이를 모니터링한다. 소비 속도 < 생산 속도면 지연이 무한히 쌓인다.

## 5. 캐싱

- **캐시는 정합성 문제를 만든다.** 넣기 전에 stale 데이터가 허용되는지 확인한다.
- 무효화 전략을 먼저 정한다: TTL(단순, 권장) / 쓰기 시 삭제 / 이벤트 기반.
- **캐시 스탬피드**: TTL 만료 순간 전부 DB 로 몰린다 → 지터 있는 TTL, 또는 단일 재생성 락.
- 캐시 미스가 정상 동작이어야 한다. 캐시가 죽으면 느려지되 **동작은 해야 한다**.
- 로봇 상태처럼 자주 바뀌는 것은 캐시보다 **push(WebSocket/SSE)** 가 낫다
  (`websocket-engineer` 스킬).

## 6. 일관성 · 트랜잭션

- 단일 DB 안에서는 트랜잭션을 쓴다. **경계를 명시**한다 — 어디서 커밋되는지 읽는 사람이 알아야 한다.
- 서비스를 넘는 트랜잭션은 **하지 않는다.** 2PC 는 실무에서 거의 쓰지 않는다.
  대신:
  - **Saga**: 각 단계마다 보상 트랜잭션을 정의
  - **Outbox 패턴**: DB 쓰기와 메시지 발행을 같은 트랜잭션으로 묶고 별도 프로세스가 발행
- **최종 일관성을 UI 에 드러낸다.** "처리 중" 상태를 사용자에게 보여준다.
  즉시 반영된 척하고 나중에 실패하면 신뢰를 잃는다.

## 7. 장애 · 성능 저하 설계

**모든 외부 호출은 실패한다고 가정한다.**

- **타임아웃**: 모든 호출에. 타임아웃 없는 호출은 버그다.
  상위 타임아웃 > 하위 타임아웃 합 이어야 한다.
- **서킷 브레이커**: 계속 실패하는 의존성을 빠르게 차단. 안 하면 스레드가 전부 대기에 묶인다.
- **격벽(bulkhead)**: 의존성별 커넥션 풀 분리. 한 서비스가 느려져도 전체가 안 죽게.
- **우아한 성능 저하**: 추천이 죽으면 인기순으로, 실시간 지표가 죽으면 마지막 값 + 시각 표시.
  전부 아니면 전무로 만들지 않는다.
- **재시도 폭풍 방지**: 백오프 + 지터 + 재시도 예산.

핵심 질문: **서버가 죽으면 로봇은?** 로봇이 서버 없이 현재 작업을 마칠 수 있게 설계하면
가용성 요구가 크게 낮아진다. 이게 전체 비용을 좌우한다.

## 8. 확장

- **수직 확장을 먼저 검토한다.** 인스턴스를 키우는 것이 분산보다 항상 싸고 단순하다.
- 앱 서버는 **무상태**로. 상태는 DB/Redis 에. 그래야 수평 확장이 가능하다.
- 병목은 대개 **DB** 다. 읽기 복제본 → 캐시 → 샤딩 순으로 검토한다. 샤딩은 최후 수단이다.
- 백프레셔를 설계한다. 처리 못 할 만큼 받으면 **거절**한다. 큐에 무한히 쌓으면 전부 죽는다.
- 부하 시험으로 확인한다. 추정만으로 "확장 가능하다"고 말하지 않는다.

## 9. 멀티테넌시 (고객사가 여럿일 때)

- 격리 수준: 논리 격리(테넌트 ID 컬럼) → 스키마 분리 → DB 분리 → 완전 분리.
  **오른쪽으로 갈수록 안전하고 비싸다.** 고객 요구와 규제로 결정한다.
- 논리 격리면 **모든 쿼리에 테넌트 필터가 강제**되어야 한다. 한 곳만 빠져도 데이터 유출이다.
  ORM 레벨에서 강제하고 테스트로 검증한다.
- 테넌트별 리소스 상한을 둔다. 한 고객이 전체를 느리게 만들 수 있다.
- 폐쇄망 고객은 아예 **온프레미스 배포**가 필요할 수 있다 (`robot-networking`, `fleet-ops`).

## 10. 관측성

로그·메트릭·트레이스 셋을 처음부터 넣는다. 나중에 넣으면 장애 때 없다.

- **구조화 로그**(JSON) + 요청 ID. 요청 ID 가 로봇 → 게이트웨이 → 서비스 → DB 까지 전파되어야 한다.
- 메트릭: 요청률·오류율·지연(p50/p95/p99)·포화도. **평균이 아니라 분위수**를 본다.
- 분산 추적(OpenTelemetry)을 서비스가 3개 넘어가면 반드시.
- **비즈니스 지표**도 함께: 작업 성공률, 로봇 가동률, 개입 횟수.
  기술 지표만으로는 "정상인데 사업이 안 되는" 상태를 못 잡는다.
- 세부는 `monitoring-expert` 스킬.

## 11. 보안

- 인증과 인가는 다르다. **로봇 인증**(mTLS/토큰)과 사용자 인증을 분리 설계한다.
- 로봇마다 다른 자격증명, 폐기·회전 가능하게 (`fleet-ops`).
- 최소 권한. 서비스 계정이 전체 DB 를 읽을 이유가 없다.
- 시크릿은 시크릿 매니저. 세부는 `authentication-patterns`, `security-hardening` 스킬.

## 설계 리뷰 체크리스트

- [ ] 수치(규모·QPS·데이터 증가율·지연·가용성)가 정의됐는가
- [ ] 지금 규모에 **가장 단순한 구조**인가. 나눈 것마다 근거가 있는가
- [ ] 서버가 죽으면 로봇/사용자는 무엇을 할 수 있는가
- [ ] 모든 외부 호출에 타임아웃이 있는가
- [ ] 재시도 가능한 쓰기가 멱등한가
- [ ] 데이터 증가율에 대해 보존·아카이빙 정책이 있는가
- [ ] 무중단 스키마 마이그레이션이 가능한가
- [ ] 부분 실패 시 UI 가 무엇을 보여주는가 (`ui-ux-design`)
- [ ] 요청 ID 가 끝까지 전파되는가
- [ ] 테넌트 격리가 강제되는가 (해당 시)
- [ ] 롤백 경로가 있는가
