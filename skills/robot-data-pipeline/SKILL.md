# 로봇 데이터 파이프라인

로봇에서 데이터는 **재수집 비용이 극단적으로 비싸다.** 한 번 놓친 현장 상황은
다시 만들 수 없는 경우가 많다. 파이프라인 설계의 제1원칙은 **일단 잘 남기는 것**이다.

## 기록 (rosbag2)

### 무엇을 기록할 것인가
- **전부 기록하면 디스크와 CPU 가 먼저 죽는다.** 토픽을 선별한다.
- 반드시 남길 것: 센서 원본(또는 압축본), TF, 오도메트리, 명령(`/cmd_vel`, 관절 명령),
  상태 기계 전이, 진단(`/diagnostics`), 파라미터 스냅샷.
- 파생 데이터(코스트맵, 시각화용 마커)는 대개 재생성 가능하므로 뺀다.
- 이미지는 `compressed`, 포인트클라우드는 필요시 다운샘플 토픽을 별도로 만들어 기록한다.

```bash
# 선별 기록 + MCAP
ros2 bag record -s mcap -o run_$(date +%Y%m%d_%H%M%S) \
  /tf /tf_static /odom /scan /camera/image_raw/compressed /cmd_vel /diagnostics

# 정규식으로 제외
ros2 bag record -a -x "/.*costmap.*|/.*markers.*"
```

### 포맷: MCAP 을 기본으로
- `db3`(SQLite)보다 **MCAP** 이 낫다 — 압축, 인덱싱, 부분 읽기, Foxglove/PlotJuggler 호환.
- 장기 보관·공유 포맷을 MCAP 으로 통일하면 도구 문제가 사라진다.

### 기록 시 주의
- **디스크 I/O 가 병목이 되면 메시지가 유실된다.** 기록 중 `ros2 bag record` 의 경고를 무시하지 않는다.
  가능하면 별도 디스크(NVMe)에 쓴다.
- QoS 불일치로 기록이 안 되는 경우가 있다. 센서가 BEST_EFFORT 면 QoS 오버라이드가 필요할 수 있다.
- 디스크 여유를 감시하고, 임계 이하면 **기록을 멈추고 알린다.** 꽉 차면 로봇 전체가 불안정해진다.
- 파일명에 로봇 ID·날짜·시나리오를 넣는다. `bag1`, `test2` 는 3일 뒤에 아무 의미가 없다.

## 메타데이터 — 이게 없으면 데이터는 쓰레기가 된다

각 bag 에 함께 저장할 것:
- 로봇 개체 ID, 하드웨어 구성, 펌웨어 버전
- 소프트웨어 버전 (git commit hash) — **필수**
- 캘리브레이션 파일 (또는 그 해시)
- 파라미터 스냅샷 (`ros2 param dump`)
- 환경 조건 (장소, 조명, 날씨, 바닥 재질)
- 시나리오 설명과 결과 (성공/실패, 무슨 일이 있었는지)

**"어떤 커밋으로 돌린 데이터인지 모르는 bag" 은 재현이 불가능하므로 분석 가치가 절반 이하다.**
기록 시작 시 자동으로 메타데이터를 남기는 스크립트를 만들어 강제한다.

## 가공

```
rosbag2/MCAP → 동기화된 프레임 추출 → 필터링 → 라벨링 → 데이터셋 포맷
```

- **시간 동기화**가 첫 단계다. 센서마다 주기가 다르므로 기준 토픽을 정하고
  가장 가까운 시각의 다른 센서 데이터를 짝짓는다. 슬롭 허용치를 명시한다
  (`robot-calibration` 스킬의 시간 동기화 참고).
- 정지 구간, 센서 이상 구간, 사람이 개입한 구간을 **자동으로 걸러내는** 필터를 만든다.
  수작업으로 하면 데이터가 늘어날수록 불가능해진다.
- 학습용이면 목적 포맷으로 변환:
  - 모방학습 → **LeRobotDataset** (Parquet + MP4) — `imitation-learning` 스킬
  - 비전 → COCO/YOLO 형식 + 이미지
  - 일반 시계열 → Parquet / HDF5

## 라벨링

- **자동 라벨링을 최대한 활용한다**: 시뮬레이션 합성 데이터(라벨 공짜),
  기존 모델의 의사 라벨 + 사람 검수, 기하학적 제약(깊이·LiDAR 로 3D 박스 생성).
- 사람 라벨링은 비싸다. **모델이 틀린 것만** 검수하는 능동학습 루프가 비용 대비 효과가 크다.
- 라벨 규약(클래스 정의, 경계 기준, 가림 처리)을 문서로 고정한다.
  작업자가 바뀌면 라벨 분포가 바뀌고, 모델 성능 변화의 원인을 못 찾게 된다.
- 라벨 품질을 샘플링 검사한다. 라벨 오류율을 모르면 모델 오차를 해석할 수 없다.

## 버저닝

- 데이터셋도 코드처럼 버전을 매긴다. DVC, Git LFS, 또는 객체 저장소 + 매니페스트.
- **모델 하나마다 학습에 쓴 데이터셋 버전을 기록**한다.
  성능이 떨어졌을 때 코드 문제인지 데이터 문제인지 구분할 수 있어야 한다.
- 데이터를 지우지 않는다. 잘못된 라벨은 수정 이력으로 남기고 원본은 보관한다.
- 분할(train/val/test)을 **고정**하고 저장한다. 매번 랜덤 분할하면 성능 비교가 무의미하다.
  같은 장면·같은 에피소드가 train 과 test 에 나뉘어 들어가지 않게 **에피소드 단위로 분할**한다.
  (프레임 단위 랜덤 분할은 성능을 과대평가하는 대표적 함정)

## 현장 → 개선 순환 (데이터 플라이휠)

```
현장 운용 → 실패 사례 자동 수집 → 라벨/검수 → 재학습 → 검증 → 배포 → 현장 운용
```

- 실패를 **자동으로 감지해 그 전후 구간만 저장**하는 구조를 만든다.
  전 구간을 저장하면 용량이 감당 안 되고, 저장 안 하면 개선할 수 없다.
  (링버퍼로 계속 물고 있다가 이벤트 발생 시 앞뒤 N초를 덤프하는 방식)
- 어떤 것을 실패로 볼지 정의한다: 개입 발생, 재계획 반복, 로컬라이제이션 신뢰도 저하,
  파지 실패, 안전 정지.
- 현장에서 개발 서버로 데이터를 올리는 경로(네트워크·용량·개인정보)를 미리 설계한다.
  현장 로봇의 업로드 대역폭은 대개 매우 제한적이다.

## 개인정보·보안

- 현장 영상에 사람 얼굴·차량 번호판이 찍힌다. **수집 단계에서 마스킹**하거나
  접근 통제를 설계한다. 고객사 데이터 반출 조건을 계약 시점에 확인한다.
- 데이터 보관 기간과 파기 정책을 정한다.

## 검증

- 데이터셋 통계를 매번 확인한다: 클래스 분포, 에피소드 길이 분포, 결측 프레임 비율.
  **분포가 치우친 데이터로 학습하고 모델을 탓하는 일이 잦다.**
- 파이프라인 자체에 테스트를 넣는다 — 변환 후 프레임 수, 타임스탬프 단조성,
  좌표계 일관성. 조용히 깨진 파이프라인은 몇 주를 낭비시킨다.
