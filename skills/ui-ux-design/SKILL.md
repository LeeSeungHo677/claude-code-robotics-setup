# UI/UX 설계

**무엇을 만드는지에 따라 좋은 UI 의 정의가 다르다.** 이걸 먼저 정하지 않으면
소비자 앱 감성으로 관제 화면을 만드는 것 같은 실수를 한다.

| 유형 | 최우선 | 하지 말 것 |
|---|---|---|
| 소비자 제품 | 첫인상, 전환, 감정 | 정보 밀도 과다 |
| **내부 도구 / 운영 콘솔** | **속도, 정보 밀도, 실수 방지** | 여백 미학, 애니메이션 |
| **관제·모니터링 대시보드** | **이상 상황 인지 속도** | 예쁜 그래프, 알람 남발 |
| 문서·설정 화면 | 찾기 쉬움, 되돌리기 | 숨겨진 고급 옵션 |

로봇 관제 콘솔은 두 번째·세 번째다. **매일 8시간 보는 사람을 위한 화면**이지
포트폴리오가 아니다.

---

## 1. 설계 순서

코드나 화면을 그리기 전에:

1. **누가 무엇을 하려고 오는가** — 역할별로 나눈다 (운영자 / 정비 / 관리자 / 개발자).
   역할이 다르면 필요한 정보가 다르다. 한 화면에 다 넣으면 아무도 못 쓴다.
2. **가장 자주 하는 3가지 작업**을 적는다. 그 3개가 **한 화면에서 클릭 2번 안에** 되어야 한다.
   나머지는 깊이 들어가도 된다.
3. **최악의 순간**을 정의한다 — 로봇이 멈췄을 때, 알람이 10개 뜰 때.
   그때 화면이 도움이 되는가. 평상시가 아니라 이때가 UI 의 존재 이유다.
4. 그 다음에 정보 구조 → 흐름 → 화면.

---

## 2. 정보 구조 · 내비게이션

- **깊이보다 넓이.** 3단계를 넘어가면 사용자가 길을 잃는다.
- 현재 위치를 항상 알 수 있게 (브레드크럼, 활성 표시).
- 그룹핑은 **사용자의 멘탈 모델**을 따른다. 시스템 구조(마이크로서비스 경계)로 나누지 않는다.
  사용자는 "로봇", "작업", "맵" 을 생각하지 `fleet-service`, `task-service` 를 생각하지 않는다.
- 검색이 내비게이션을 대체할 수 있는지 검토한다. 항목이 많으면 검색이 메뉴보다 빠르다.
- **URL 이 상태를 담게 한다.** 특정 로봇의 특정 탭을 링크로 공유할 수 있어야 현장에서 쓸 만하다.

---

## 3. 디자인 시스템 — 토큰부터

> 척도 설계·검증·기존 화면 개선 순서는 **`design-system` 스킬**에 상세히 있다.

값을 그때그때 정하지 않는다. **척도(scale)를 먼저 정하고 거기서만 고른다.**

```
간격   4 8 12 16 24 32 48 64          (4px 배수, 예외 없이)
글자   12 14 16 20 24 32 40           (본문 14~16, 이보다 작은 건 캡션만)
행간   본문 1.5 / 제목 1.2
모서리 0 4 8 12 (전체적으로 하나의 성격 유지)
그림자 3단계면 충분 (표면 높이를 나타낼 때만)
```

**색은 역할로 정의한다.** `blue-500` 이 아니라 `--color-primary`, `--color-danger`,
`--surface-1`, `--text-muted`. 색상값을 컴포넌트에 직접 쓰면 테마 변경이 불가능해진다.

상태 색 규약 — **의미를 고정하고 절대 재사용하지 않는다**:
```
정상/성공   green      주의/저하   amber      오류/위험   red
정보/진행   blue       비활성      gray       알 수 없음  gray + 빗금·물음표
```
"알 수 없음"을 회색으로만 두면 "정상"으로 오인된다. **패턴이나 아이콘을 함께** 준다.
색맹 사용자에게 red/green 만으로 구분되는 UI 는 정보를 전달하지 못한다 —
**색 + 아이콘 + 텍스트** 세 겹으로 준다.

---

## 4. 컴포넌트 상태 — 여기서 대부분의 UI 가 무너진다

모든 데이터 표시 컴포넌트는 **최소 5가지 상태**를 설계해야 한다.

| 상태 | 흔한 실수 |
|---|---|
| **로딩** | 스피너만 돌림 → 스켈레톤으로 최종 레이아웃을 미리 보여준다 (레이아웃 점프 방지) |
| **비어 있음** | "데이터 없음" 만 표시 → **왜 비었는지 + 다음에 뭘 할지**를 준다 |
| **오류** | "오류가 발생했습니다" → **무엇이 실패했고 재시도가 가능한지**를 준다 |
| **부분 실패** | 아예 설계 안 함 ← **가장 자주 빠뜨린다.** 로봇 10대 중 3대만 응답할 때 화면은? |
| 정상 | — |

부분 실패는 분산 시스템 UI 의 기본 조건이다. **응답한 것은 보여주고, 응답 없는 것은
명시적으로 "알 수 없음"** 으로 표시한다. 조용히 빼면 사용자는 그 로봇이 없다고 생각한다.

## 5. 운영자 대시보드 UX

로봇 관제 콘솔을 만든다면 이 절이 핵심이다.

### 시선 배치
- **왼쪽 위가 가장 비싼 자리**다. 여기에 "지금 문제가 있는가"를 놓는다.
- 상시 표시 = 이상을 인지하는 데 필요한 것만. 나머지는 클릭해서 들어간다.
- 로봇이 20대면 20개 카드를 다 보여주지 않는다. **문제 있는 것만 위로 정렬**하고
  정상은 요약 숫자로 접는다. ("정상 17 / 주의 2 / 오류 1")

### 알람 설계 — 알람 피로가 가장 큰 실패
- **행동 가능한 것만 알람으로 만든다.** 사용자가 아무것도 할 수 없는 알람은 소음이다.
- 심각도를 3단계 이하로. 5단계를 만들면 아무도 구분하지 않는다.
- **중복 억제**: 같은 원인의 알람 10개를 하나로 묶는다. 한 로봇이 통신 두절이면
  그 로봇의 센서 알람 5개를 따로 띄우지 않는다.
- 확인(ack) 과 해소(resolve) 를 구분한다. 사람이 봤다는 것과 문제가 없어졌다는 것은 다르다.
- 알람에 **다음 행동**을 함께 넣는다: "재도킹 시도" 버튼, "로그 보기" 링크.
- 소리 알람은 신중하게. 하루 종일 울리면 스피커를 끄고, 그러면 진짜 알람도 놓친다.

### 실시간 데이터
- **깜빡임을 만들지 않는다.** 값이 매 초 바뀌면 읽을 수 없다. 표시 주기를 1~2초로 조이거나
  변화가 임계 이상일 때만 갱신한다.
- 마지막 갱신 시각을 표시한다. **멈춘 화면과 변화 없는 화면을 구분**할 수 있어야 한다.
  연결이 끊기면 화면 전체에 명시적으로 표시한다 (조용히 옛 값을 보여주는 것이 최악).
- 값 + **추세**를 함께 준다. 배터리 40%보다 "40% ↓ 30분 내 충전 필요" 가 유용하다.
- 차트는 번들 스킬 `dataviz` 를 따른다.

### 지도 화면
- 로봇 위치·경로·상태를 지도에 겹칠 때, **레이어를 켜고 끌 수 있게** 한다.
  전부 겹치면 아무것도 안 보인다.
- 로봇 아이콘에 방향(heading)을 표시한다. 점만 있으면 어디를 향하는지 모른다.
- 클릭 → 상세로 가는 경로가 있어야 한다.

### 위험한 동작
- 로봇을 움직이거나 정지시키는 버튼은 **확인 단계**를 둔다.
- 되돌릴 수 없는 것(작업 취소, 맵 삭제)은 **무엇이 사라지는지 명시**하고 확인.
- 파괴적 버튼과 일상 버튼을 붙여 놓지 않는다.
- **비상 정지는 반대로** — 확인 없이 즉시. 크고, 항상 같은 자리에.

## 6. 폼 설계

- 라벨은 **항상 보이게**. placeholder 를 라벨로 쓰면 입력 시작하는 순간 무엇을 넣는지 잊는다.
- 검증은 **필드를 벗어날 때**. 타이핑 중 빨간 에러를 띄우지 않는다.
- 오류 메시지는 **무엇이 잘못됐고 어떻게 고치는지**. "잘못된 입력" 은 도움이 안 된다.
- 단위를 필드 안에 표시한다 (m/s, Hz, ms). 로봇 설정 화면에서 특히 중요하다.
- 기본값을 잘 주면 폼의 절반이 사라진다.
- 긴 폼은 나누되 **진행 상황과 되돌아가기**를 제공한다.
- 파괴적 작업 전 확인은 "정말?" 이 아니라 **이름을 입력하게** 하는 식으로 마찰을 준다.

---

## 7. 마이크로카피

- **사용자의 언어**를 쓴다. "노드", "토픽", "QoS" 는 개발자 언어다.
  운영자에게는 "센서 연결", "통신 상태" 로 말한다.
- 오류: 무엇이 / 왜 / 어떻게 → 세 요소. "연결 실패 (30초 무응답). 네트워크를 확인하거나 재시도하세요."
- 빈 상태: "아직 등록된 로봇이 없습니다. [로봇 추가]" — 다음 행동을 준다.
- 버튼은 **동사**로. "확인" 보다 "작업 취소", "저장" 이 명확하다.
- 사과하지 않는다. 무엇을 해야 하는지 알려준다.

---

## 8. 반응형 · 접근성

- 현장에서 **태블릿**으로 볼 수 있다. 터치 대상은 최소 44px.
- 데이터 표는 좁은 화면에서 가로 스크롤 컨테이너에 넣는다. 페이지 전체가 흔들리면 안 된다.
- 키보드만으로 전 기능이 되는가. 포커스 표시가 보이는가.
- 명도 대비 4.5:1 이상 (본문). 현장 조명이 밝으면 더 높게.
- 세부는 `accessibility-wcag` 스킬.

---

## 9. 다크 모드

- **색을 반전시키는 것이 아니다.** 표면 단계(surface elevation)를 다시 설계한다.
  다크에서는 밝을수록 위에 있는 것으로 읽힌다.
- 순검정(#000) 배경 + 순백(#fff) 텍스트는 눈이 아프다. 약간 띄운 값을 쓴다.
- 채도 높은 색은 다크에서 진동한다. 채도를 낮춘 변형을 따로 만든다.
- 상태 색(red/amber/green)이 다크에서도 대비를 만족하는지 **각각 검증**한다.

---

## 10. 디자인 → 구현 핸드오프

- 토큰을 **코드로 전달**한다 (CSS 변수 / 테마 객체). 이미지나 스펙 문서로 넘기면 어긋난다.
- 상태별 화면을 전부 준다 (로딩/빈/오류/부분실패). 정상 화면만 주면 나머지는 구현자가 지어낸다.
- 엣지 케이스를 명시: 이름이 매우 길 때, 항목이 0개일 때, 1000개일 때.
- 시각적 완성도(타이포 스케일·간격 리듬·색 충돌·tabular-nums)는 **`design-system` 스킬**.
  "기능은 되는데 디자인이 아쉽다" 는 대개 여기서 해결된다.
- 구현은 `frontend-design`(개성·심미 — 제품/랜딩용), `frontend-excellence`(성능) 스킬.

---

## 11. 검증

- **5명이면 대부분의 문제가 나온다.** 정식 사용성 테스트가 아니어도 좋다.
  실제 운영자에게 "지금 어느 로봇이 문제인지 찾아보세요" 하고 **말없이 지켜본다.**
- 시간을 잰다. 자주 하는 작업이 몇 초 걸리는지가 내부 도구의 핵심 지표다.
- 현장 조명·소음·장갑 낀 손 조건에서 시험한다. 사무실에서 잘 되는 것과 다르다.
- 배포 후: 어느 화면에서 이탈하는지, 어떤 알람이 무시되는지를 측정한다.

## 흔한 실수

| 실수 | 결과 |
|---|---|
| 모든 정보를 한 화면에 | 아무것도 안 보임 |
| 부분 실패 상태 미설계 | 응답 없는 로봇이 화면에서 사라짐 |
| 알람 심각도 5단계 | 아무도 구분 안 함 |
| 색만으로 상태 구분 | 색맹 사용자에게 정보 전달 실패 |
| 마지막 갱신 시각 없음 | 멈춘 화면을 정상으로 오인 |
| 개발자 용어 그대로 노출 | 운영자가 문의 전화를 함 |
| 예쁜 애니메이션 | 매일 8시간 보면 방해가 됨 |
| 비상 정지에 확인 대화상자 | 위급 시 1초가 늦어짐 |
