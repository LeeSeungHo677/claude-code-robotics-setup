# 현장 장애 분석

현장에서 무슨 일이 있었는지는 **로그로만 재구성된다.**
기억과 증언은 틀린다. 이 문서는 재구성 절차와 재발 방지 절차다.

## 사고 직후 (현장에서 즉시)

**증거를 먼저 확보한다.** 재부팅하면 사라지는 것들이 있다.

- [ ] **재부팅하지 않는다.** 상태를 그대로 두고 먼저 수집한다
- [ ] rosbag(링버퍼가 있으면 덤프), 전체 로그, 코어덤프
- [ ] `ros2 param dump` — 그 시점 파라미터
- [ ] 소프트웨어 버전 / 커밋 해시 / 컨테이너 이미지 태그
- [ ] 현장 사진 (로봇 위치, 주변 상황, 바닥 상태)
- [ ] 목격자 진술을 **시각과 함께** 즉시 기록 (시간이 지나면 각색된다)
- [ ] 관제 서버 로그 (로봇 쪽만으로는 부족하다)
- [ ] 안전이 관련되면 **작업 중단**하고 보고 체계를 따른다

이 수집을 자동화하는 명령을 미리 만들어 두는 것이 최선이다
(`fleet-ops` 스킬의 진단 번들).

## 재구성

### 타임라인을 먼저 만든다
분석 전에 **무엇이 언제 일어났는지**를 시각 순으로 나열한다.

```
14:23:01.2  작업 배정 (관제) — pick@A12
14:23:04.8  경로 계획 성공, 길이 34m
14:23:41.0  로컬라이제이션 공분산 급증 (0.02 → 0.31)
14:23:41.5  [문제 시작] 재계획 반복 시작
14:23:52.1  회복 동작 3회 실패
14:23:53.0  충돌 감지 → 안전 정지
```

- 모든 소스의 시각을 **하나의 기준으로 정렬**한다. 로봇/관제 시계가 다르면 먼저 보정한다.
  (시간 동기화가 안 돼 있으면 여기서 분석이 막힌다 → `robot-networking`)
- **"문제 시작 시점" 과 "증상 발현 시점" 을 구분**한다. 대개 몇 초~몇 분 차이가 있고,
  원인은 시작 시점에 있다. 증상 시점만 보면 결과를 원인으로 오인한다.

### 계층별 배제
`/robot:diagnose` 의 순서를 사후 분석에도 적용한다:
프로세스 생존 → 토픽 흐름 → QoS → 시간 → TF → 좌표계 → 캘리브레이션 → 알고리즘.

rosbag 이 있으면 **오프라인 재현**을 시도한다. 재현되면 원인 규명은 시간 문제다.
재현이 안 되면 타이밍·경합·환경 요인을 의심한다.

## 근본원인 — 여기서 대부분 실패한다

**"센서가 오작동했다" 는 근본원인이 아니다.** 다섯 번 더 묻는다.

```
왜 충돌했나?          → 장애물을 못 봤다
왜 못 봤나?           → LiDAR 사각지대의 낮은 팔레트였다
왜 사각지대가 있나?    → 2D 스캐너 하나만 장착
왜 하나만 장착했나?    → 위험성 평가에서 낮은 장애물을 고려하지 않았다
왜 고려하지 않았나?    → 평가 체크리스트에 해당 항목이 없었다   ← 근본원인
```

- 근본원인은 대개 **개인의 실수가 아니라 프로세스의 공백**이다.
  "누가 잘못했나" 로 끝나면 반드시 재발한다.
- 원인이 여러 개일 수 있다. 하나로 억지로 좁히지 않는다.
  단일 실패가 사고로 이어졌다면 **방어층이 하나뿐이었다는 것 자체**가 문제다.
- **왜 미리 못 잡았나**도 함께 묻는다: 테스트에 없었나, 시뮬에서 재현 안 됐나,
  모니터링에 지표가 없었나. 이게 재발 방지의 실제 재료다.

## 재발 방지 — 조치의 강도 순서

약한 조치로 끝내면 재발한다. 위에서부터 검토한다.

| 강도 | 조치 | 예 |
|---|---|---|
| 강함 | **구조적 제거** | 사각지대 없는 센서 배치, 단방향 통로로 맵 변경 |
| | **자동 검출·차단** | 훅/린트/런타임 검증, 안전 감시자 추가 |
| | **자동 테스트** | 사고 시나리오를 회귀 테스트로 |
| | 모니터링·알림 | 지표 추가해 조기 감지 |
| 약함 | 문서·교육 | 매뉴얼 보완, 운영자 교육 |
| 매우 약함 | "주의하기로 함" | ← 조치가 아니다 |

**사고 하나당 최소 하나의 자동화된 방어**를 만드는 것을 원칙으로 한다.

### 회귀 테스트 만들기
- 사고 당시 rosbag 을 **회귀 테스트 자산**으로 등록한다.
- 시뮬레이션으로 재현 가능하면 시나리오를 CI 에 넣는다 (`gazebo` 스킬의 결정론 참고).
- 인지 실패였다면 그 프레임을 인지 회귀 세트에 추가한다 (`deep-learning-vision`).

## 보고서

고객사·내부용 형식 (8D, 5-Why, 또는 자체 양식):

```
1. 사건 개요      — 언제, 어디서, 무엇이, 영향(인명/설비/가동중단 시간)
2. 즉시 조치      — 현장에서 무엇을 했나
3. 타임라인       — 시각별 사실 (추측과 분리)
4. 근본원인       — 5-why, 기여 요인 포함
5. 재발 방지      — 조치·담당·기한·검증 방법
6. 검증 결과      — 조치가 실제로 효과 있는지 확인한 방법
7. 남은 위험      — 이 조치로 커버되지 않는 것
```

- **사실과 추측을 명확히 구분해 쓴다.** "~로 추정된다" 와 "~였다" 를 섞지 않는다.
  로그로 확인한 것만 사실로 쓴다.
- 확인하지 못한 것은 "확인 불가" 로 남긴다. 그럴듯한 이야기로 메우지 않는다.
- 고객사 제출용은 기술 용어를 풀어 쓰되 **사실을 축소하지 않는다.**

## 플릿 규모의 장애 관리

- 장애를 **유형별로 분류·집계**한다. 같은 유형이 반복되면 개별 대응이 아니라 설계 문제다.
- 개입 횟수·유형이 현장 품질의 핵심 지표다 (`fleet-ops`, `teleoperation`).
- 링버퍼로 상시 기록하다가 **이벤트 발생 시 앞뒤 N초를 자동 덤프**하는 구조를 만든다.
  전 구간 저장은 용량이 감당 안 되고, 저장 안 하면 분석이 불가능하다
  (`robot-data-pipeline`).
- 장애 데이터가 곧 개선 재료다. 분석하고 버리지 말고 축적한다.

## 태도

- 사고 분석에서 **결론을 서두르지 않는다.** 첫 번째로 눈에 띄는 원인이 진짜인 경우는 드물다.
- 재현되지 않는 문제를 "해결됐다" 고 하지 않는다. 원인을 모르면 모른다고 한다.
- 안전이 관련된 사건은 규격·법적 보고 의무가 있을 수 있다 (`robot-safety-compliance`).
