# 다중 로봇 관제

로봇 한 대의 문제와 **성격이 다르다.** 개별 로봇이 각각 최적으로 움직이면
전체는 교착에 빠진다. 여기서 다루는 것은 **전역 조율**이다.

## 먼저: 중앙 집중인가 분산인가

| | 중앙 집중 | 분산 |
|---|---|---|
| 최적성 | 높음 (전역 정보) | 낮음 (지역 정보) |
| 단일 장애점 | **있음** — 관제가 죽으면 전체 정지 | 없음 |
| 확장성 | 수십 대까지 무난 | 수백 대 |
| 디버깅 | 쉬움 (한 곳에 상태가 있음) | 어려움 |
| 적합 | 창고·공장 (환경이 고정, 규모가 정해짐) | 야외·대규모·통신 불안정 |

**공장/창고는 대개 중앙 집중이 정답이다.** 다만 **관제가 죽었을 때 로봇이 무엇을 하는지**를
반드시 정의한다 — 대개 "현재 작업만 마치고 안전 정지". 관제 없이 계속 새 작업을 시작하면 안 된다.

## 작업 할당 (Task Allocation)

| 방식 | 특징 |
|---|---|
| **최근접 로봇** | 단순, 대부분의 소규모 현장에서 충분. 먼저 시도한다 |
| **경매/입찰(auction)** | 각 로봇이 비용(거리+배터리+현재 작업)을 입찰. 분산 가능, 준최적 |
| **헝가리안 / 최적 할당** | 작업-로봇 수가 비슷하고 한 번에 배정할 때. 다항시간 최적 |
| **MILP / CP** | 시간창·우선순위·용량 제약이 많을 때. 계산 비용 큼 |
| **학습 기반** | 패턴이 반복적이고 데이터가 충분할 때. 설명 가능성이 떨어진다 |

- **비용 함수가 전부다.** 거리만 쓰면 배터리 낮은 로봇에 먼 작업이 배정된다.
  최소한 `거리 + 배터리 여유 + 현재 작업 잔여 + 혼잡도` 를 넣는다.
- **재할당(re-assignment)** 정책을 정한다. 더 좋은 로봇이 생겼을 때 이미 배정된 작업을
  뺏을 것인가. 뺏으면 최적이지만 로봇이 우왕좌왕한다. 대개 **이동 시작 전까지만** 재할당을 허용한다.
- 굶주림(starvation) 방지: 오래 기다린 작업의 우선순위를 시간에 따라 올린다.
  안 하면 접근성 나쁜 위치의 작업이 영원히 밀린다.

## 교통 관리 (Traffic Management)

다중 로봇의 **진짜 어려운 부분**이다.

### 접근 방식
- **예약(reservation) 기반**: 경로상의 셀/구간을 시간과 함께 예약. 충돌이 원천 차단된다.
  Open-RMF 의 traffic schedule 이 이 방식.
- **우선순위 + 회피**: 마주치면 규칙(오른쪽 우선, ID 낮은 쪽 우선)으로 한쪽이 양보.
  단순하지만 좁은 통로에서 교착이 난다.
- **속도 조절**: 경로는 유지하고 속도만 조절해 시공간 충돌을 피한다 (velocity tuning).
  경로 재계획보다 안정적이다.

### 교착(deadlock) — 반드시 설계해야 한다
좁은 통로에서 두 로봇이 마주보면 **자동으로 풀리지 않는다.**

- **탐지**: 일정 시간 이상 진행이 없는 로봇 집합을 감지한다. 대기 그래프에서 순환을 찾는다.
- **해소**: 우선순위가 낮은 로봇이 **후퇴 가능한 지점(passing bay)** 까지 물러난다.
  후퇴 지점이 맵에 정의돼 있어야 한다 — 없으면 사람이 가서 밀어야 한다.
- **예방이 최선**: 단방향 통로, 교행 지점 지정, 좁은 구간의 동시 진입 제한(뮤텍스 구간).
  맵 설계 단계에서 정하는 것이 알고리즘으로 푸는 것보다 훨씬 싸다.
- 교착 발생 횟수를 **지표로 기록**한다. 늘어나면 맵이나 작업 분포에 문제가 있는 것이다.

## Open-RMF

여러 벤더의 로봇 플릿과 건물 인프라(문·엘리베이터·디스펜서)를 하나의 관제로 묶는 오픈소스 프레임워크.
**로봇을 직접 제어하지 않고, 각 플릿의 API 를 통해 조율한다.**

### 구조
```
Task Dispatcher  ── 작업을 어느 플릿에 줄지 결정
Traffic Schedule ── 모든 로봇의 "의도된 미래 궤적" 중앙 DB. 충돌을 미리 찾아 알림
Negotiation      ── 충돌 시 플릿들이 협상해 대안 궤적 합의
Fleet Adapter    ── 플릿별 어댑터. 벤더 API ↔ RMF 인터페이스 변환
Building Map     ── traffic_editor / building_map_generator 로 만든 내비게이션 그래프
Infrastructure   ── door / lift / dispenser / ingestor 어댑터
```

**핵심 개념: traffic schedule 은 과거가 아니라 미래를 담는다.**
각 로봇이 "앞으로 이 경로를 이 시각에 지나겠다"를 등록하고, 스케줄이 충돌을 찾아낸다.

### 도입 판단
- **적합**: 여러 벤더 로봇 혼용, 엘리베이터·자동문 연동 필요, 다층 건물, 표준화된 관제 요구
- **과함**: 자사 로봇 5대 이하, 단층, 인프라 연동 없음 → 직접 만든 관제가 더 빠르고 디버깅이 쉽다

RMF 는 학습 곡선이 가파르다. **먼저 `rmf_demos` 를 그대로 돌려보고**
자기 환경으로 바꾸는 순서를 권한다. 처음부터 자기 플릿으로 시작하면 무엇이 문제인지 알 수 없다.

### Fleet Adapter 구현
- `fleet_adapter_template` 를 출발점으로 쓴다.
- 어댑터가 책임지는 것: 로봇 상태 보고(위치·배터리·작업), 경로 명령 수행, 인프라 요청 중계.
- **full control vs read-only** 를 먼저 정한다. RMF 가 경로까지 지시할 것인가,
  아니면 로봇이 스스로 가고 위치만 보고할 것인가. 후자가 도입이 쉽고 조율 효과는 약하다.
- 로봇의 실제 위치와 RMF 가 믿는 위치가 어긋나면 스케줄 전체가 무의미해진다.
  **위치 보고 주기와 지연**을 어댑터 설계에서 가장 먼저 확인한다.

### Navigation Graph
- traffic_editor 로 만든 그래프의 **웨이포인트·레인이 실제 주행 가능한 경로**와 일치해야 한다.
  그래프상 통과 가능한데 실제로는 못 지나가는 지점이 하나 있으면 그 로봇은 계속 실패한다.
- 레인에 속성을 준다: 단방향, 속도 제한, 문 통과, 특정 플릿 전용.
- 맵이 바뀌면 그래프도 바꿔야 한다. **맵과 그래프의 버전을 함께 관리**한다.

## 충전 · 도킹 스케줄링

플릿 가동률을 좌우하는데 자주 나중으로 미뤄진다.

- 충전 시작 임계를 **작업 소요 예측**과 함께 판단한다. 고정 임계(예: 30%)만 쓰면
  긴 작업 중간에 방전되거나 불필요하게 자주 충전한다.
- 충전기 수 < 로봇 수이면 충전기도 **경합 자원**이다. 예약제로 관리한다.
- 도킹 실패(정렬 실패, 충전기 점유)를 재시도 상한과 함께 처리한다.
  무한 재시도하면 로봇이 충전기 앞에서 밤새 대기한다.
- 피크 시간에 충전을 피하도록 스케줄링하면 가동률이 오른다.

## 맵 · 위치 공유

- **모든 로봇이 같은 맵과 같은 원점을 쓰는지** 확인한다. 개체마다 맵을 따로 만들면
  좌표가 미묘하게 달라 관제가 계산한 위치와 실제가 어긋난다.
- 맵 갱신은 **버전 관리 + 전 로봇 동시 반영**이어야 한다.
  일부만 새 맵을 쓰면 서로 다른 세계에서 움직이게 된다.
- 협조 SLAM(맵 병합)은 연구 주제로는 매력적이지만 현장에서는
  **한 번 잘 만든 맵을 공유하고 각자 AMCL 로 측위**하는 구조가 훨씬 안정적이다.

## 관제 시스템이 발행해야 할 것

현장 운영에서 이게 없으면 아무것도 진단할 수 없다:
- 로봇별: 현재 위치, 상태, 배정된 작업, 배터리, 마지막 통신 시각
- 작업별: 대기/진행/완료/실패, 대기 시간, 재할당 이력
- 시스템: 교착 발생 횟수, 평균 작업 완료 시간, 로봇 가동률, 개입 횟수

## 자주 터지는 것

| 증상 | 원인 |
|---|---|
| 특정 구간에서 항상 막힘 | 맵 설계 — 단방향/교행 지점 미지정 |
| 로봇이 서로 양보만 함 | 우선순위 규칙에 결정론적 tie-break 이 없음 |
| 관제가 믿는 위치와 실제가 다름 | 위치 보고 지연, 또는 로봇별 맵/원점 불일치 |
| 일부 작업이 영원히 대기 | 굶주림 — 대기 시간 기반 우선순위 상승 없음 |
| 로봇이 다 충전기로 몰림 | 충전 임계가 동일 + 충전기 예약 없음 |
| 관제 재시작 후 혼란 | 상태 영속화 없음 — 진행 중 작업 복구 설계 필요 |
| 대수를 늘리니 통신이 죽음 | DDS 디스커버리 폭주 → Discovery Server / Zenoh (`ros2-engineering`) |
