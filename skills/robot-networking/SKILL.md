# 로봇 네트워크 · 폐쇄망

로봇 네트워크는 사무실 네트워크가 아니다. **움직이면서 끊기지 않아야 하고,
고객사 망 정책 안에서 동작해야 한다.** 여기서 막히면 아무리 좋은 소프트웨어도 배포가 안 된다.

## 가장 먼저 확인할 것 — 고객사 망 정책

현장 투입 **전에** 문서로 받아둔다. 나중에 알면 일정이 무너진다.

- [ ] 인터넷 접속이 되는가. 안 된다면 완전 차단인가 프록시 경유인가
- [ ] 로봇을 어느 VLAN/서브넷에 둘 것인가. 다른 대역과 통신이 되는가
- [ ] **멀티캐스트가 허용되는가** ← DDS 디스커버리의 생사가 걸려 있다
- [ ] 방화벽에서 열 수 있는 포트 범위
- [ ] 무선 AP 를 우리가 설치하는가, 고객사 것을 쓰는가
- [ ] 외부 원격 접속이 허용되는가 (지원·유지보수에 직결)
- [ ] 보안 검토·승인 절차와 소요 기간
- [ ] MAC 주소 등록, 802.1X 인증 필요 여부

## 무선 — 움직이는 로봇의 핵심 문제

### 로밍 (AP 간 이동)
- 일반 WiFi 의 AP 핸드오프는 **수백 ms~수 초**가 걸린다. 그동안 통신이 끊긴다.
  주행 중 이 끊김이 제어·관제에 어떤 영향을 주는지 설계에 반영해야 한다.
- 대응:
  - **로밍 지원 표준**(802.11r 고속 전환, k/v 로 AP 선택 보조)을 AP·클라이언트 양쪽에서 켠다
  - AP 배치를 **중첩(overlap)** 되게 한다. 신호가 끊긴 뒤 찾는 것이 아니라 미리 넘어가게
  - 산업용 무선(AGV 전용 로밍 최적화 제품군)은 핸드오프를 수 ms 수준까지 낮춘다.
    가동률이 중요한 현장이면 검토할 가치가 있다
  - 클라이언트(로봇) 쪽 드라이버의 로밍 공격성(roaming aggressiveness)을 조정한다
- **주행 경로를 따라 실측**한다. 앉아서 설계한 커버리지는 항상 틀린다.
  로봇에 태워 RSSI·재전송률·핑 손실을 기록하며 한 바퀴 돌린다. 사각지대가 반드시 나온다.

### DDS over WiFi — 그대로 쓰면 안 된다
- 무선은 유선보다 **손실·지연·지터가 크고 멀티캐스트가 특히 취약**하다.
  많은 AP 가 멀티캐스트를 최저 속도로 보내거나 아예 막는다.
- 대응:
  - **디스커버리를 유니캐스트로**: CycloneDDS `Peers` 목록, FastDDS **Discovery Server**
  - 무선 구간으로 대용량 토픽(포인트클라우드, 원본 이미지)을 보내지 않는다.
    필요하면 압축·다운샘플·주기 축소
  - 센서 토픽은 BEST_EFFORT + 얕은 depth. RELIABLE 로 두면 재전송이 폭주해 더 나빠진다
  - 무선 구간을 **DDS 도메인 경계**로 만들고 브리지(Zenoh, MQTT, 전용 API)로 넘긴다.
    로봇 내부는 DDS, 로봇↔관제는 브리지 — **이 구조를 기본으로 권한다**

### 알아둘 함정
- **네트워크가 완전히 끊기면 같은 기기 안의 노드 간 통신까지 영향받을 수 있다.**
  (인터페이스가 내려가면 DDS 가 로컬 통신도 잃는 사례가 보고돼 있다)
  → 온보드 제어에 필수인 노드들은 네트워크 상태와 무관하게 동작하도록
  **loopback 을 명시적으로 활성화**하거나 SHM 전송을 쓰고, 실제로 랜선을 뽑고 시험한다.
- 로봇 온보드 스택이 관제 연결에 의존하지 않게 만든다. **통신이 끊겨도 안전하게 정지**할 수 있어야 한다.

## 폐쇄망 (Air-gapped) 배포

인터넷이 없는 현장이 흔하다. 준비 없이 가면 아무것도 설치할 수 없다.

### 반입 전 준비 (사내에서 미리)
```bash
# 1) 컨테이너 이미지를 파일로
docker save myorg/robot:abc1234 | gzip > robot_abc1234.tar.gz
#    현장에서
gunzip -c robot_abc1234.tar.gz | docker load

# 2) apt 패키지 (의존성까지 전부)
apt-get install --download-only --reinstall -o Dir::Cache::archives=./debs ros-humble-nav2-bringup
#    현장에서: dpkg -i ./debs/*.deb  또는 로컬 저장소 구성

# 3) pip 패키지
pip download -r requirements.txt -d ./wheels --platform manylinux2014_x86_64 --only-binary=:all:
pip install --no-index --find-links=./wheels -r requirements.txt
```

- **컨테이너 이미지 방식을 기본으로 권한다.** 의존성 문제가 한 번에 사라진다.
- 이미지 태그를 커밋 해시로 고정한다. 현장에서 `latest` 는 재현 불가능을 뜻한다.
- 반입 매체(USB)의 반입 승인·바이러스 검사 절차를 미리 확인한다. 이게 반나절을 잡아먹는다.
- **모델 가중치, 맵, 캘리브레이션 파일**도 같이 챙긴다. 코드만 챙기고 현장에서 발견하는 일이 흔하다.
- 라이선스 활성화가 인터넷을 요구하는 소프트웨어가 있는지 사전 확인한다.

### 폐쇄망 내부에 둘 것
- 로컬 컨테이너 레지스트리 (현장 서버에 하나)
- 시간 서버 (NTP/PTP) — **인터넷 NTP 에 의존하면 폐쇄망에서 시간이 안 맞는다**
- 로그·데이터 수집 서버 (외부로 못 보내니 내부에 쌓고 주기적으로 반출)
- 필요하면 로컬 apt/pip 미러

### 업데이트 경로
- 폐쇄망에서는 OTA 가 자동으로 안 된다. **반입 → 로컬 레지스트리 → 배포** 절차를 문서화한다.
- 롤백용 이전 버전 이미지를 현장에 **남겨둔다.** 문제가 생겨도 인터넷에서 다시 못 받는다.

## 원격 접속 (지원·유지보수)

- 고객사 방화벽 뒤로 인바운드 접속은 대개 불가능하다. **로봇에서 나가는 아웃바운드 연결**로 설계한다.
- 메시 VPN(WireGuard 기반 도구 등) 또는 관제 경유 명령 채널.
  단, 폐쇄망이면 이것도 안 되므로 **현장 방문 절차**를 전제로 한 진단 도구가 필요하다.
- 원격에서 로봇을 **움직일 수 있게** 할 것인지는 안전 검토 대상이다. 기본은 조회만.
- 원격 접속이 불가능한 현장을 위해: 진단 번들 자동 수집 → USB 로 반출하는 명령을 만들어 둔다.

## 네트워크 설계 권고

- 로봇 트래픽을 **별도 VLAN** 으로 분리한다. 사무망과 섞으면 브로드캐스트에 영향받고
  보안 검토도 복잡해진다.
- 우선순위(QoS)를 건다: 제어·안전 > 관제 상태 > 영상 > 로그 업로드.
  대역폭이 부족할 때 무엇을 버릴지 미리 정하는 것이다.
- 고정 IP 또는 DHCP 예약을 쓴다. 로봇 IP 가 바뀌면 관제 설정이 깨진다.
- 시간 동기화를 반드시 구성한다 (`robot-calibration`, `ros2-engineering/multi-robot.md`).
- **셀룰러(LTE/5G)** 는 실외·광역에 유효하지만 지연·요금·커버리지를 실측해야 한다.
  실내 공장에서는 대개 WiFi 가 낫다.

## 진단

```bash
# 무선 품질 (주행하며 기록)
iw dev wlan0 link ; iw dev wlan0 station dump   # RSSI, 재전송, 비트레이트
watch -n1 'iw dev wlan0 link | grep -E "signal|bitrate"'

# 끊김·지연
ping -i 0.2 <관제IP> | ts          # 손실 구간 확인
mtr -rwc 100 <관제IP>              # 경로별 손실

# DDS 관점
ros2 topic hz <topic>              # 실제 수신 주기
ros2 daemon stop && ros2 node list # 디스커버리 재확인

# 멀티캐스트 가능 여부
ros2 multicast receive   # 다른 기기에서: ros2 multicast send
```

**주행 중 로그를 시각·위치와 함께 기록**한다. "가끔 끊긴다"는 위치와 겹쳐 봐야 원인이 보인다.
대개 특정 구역에서만 발생한다.

## 증상 → 원인

| 증상 | 원인 |
|---|---|
| 벤치에서는 되는데 현장에서 안 됨 | 멀티캐스트 차단, VLAN 분리, 방화벽 |
| 주행 중 특정 구역에서만 끊김 | AP 커버리지 사각, 로밍 실패 |
| 토픽이 뚝뚝 끊김 | 무선 대역폭 초과 — 대용량 토픽을 무선으로 보내는 중 |
| 로봇 대수를 늘리니 전체가 느려짐 | DDS 디스커버리 폭주 — Discovery Server/Zenoh 전환 |
| 네트워크 끊기니 로봇 내부까지 멈춤 | 로컬 통신이 네트워크 인터페이스에 의존 — loopback/SHM 확인 |
| 시간이 안 맞음 | 폐쇄망에서 외부 NTP 참조 중 — 내부 시간 서버 필요 |
| 관제 연결이 자주 재수립됨 | keepalive/타임아웃 설정, NAT 세션 만료 |
