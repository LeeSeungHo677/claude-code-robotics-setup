# 플릿 운영 · 배포 · 납품

개발이 끝나는 지점이 아니라 **여기서부터 진짜 비용이 발생한다.**
"내 노트북에서는 됩니다" 와 "고객사에서 6개월째 무사고" 사이의 거리를 다루는 스킬이다.

## 배포 단위

```
로봇 온보드   : ROS 2 스택, 컨테이너, 설정, 캘리브레이션
엣지/현장 서버 : 플릿 관제, 맵 서버, 로그 수집 (선택)
클라우드      : 대시보드, 데이터 저장, 모델 학습, 원격 지원
```

**버전을 함께 관리한다.** 로봇 v1.3 과 관제 v2.0 이 호환되는지 표로 관리하지 않으면
현장에서 부분 업데이트가 시스템을 깨뜨린다. 호환성 매트릭스를 만들고 CI 에서 검증한다.

## 컨테이너

- 개발용과 배포용 이미지를 분리한다. 배포 이미지에 컴파일러·디버거·소스를 넣지 않는다
  (멀티스테이지 빌드). `docker-ros2-development` 스킬 참고.
- **ARM(Jetson) 타깃이면 크로스 빌드 또는 네이티브 빌드**를 정한다.
  x86 에서 빌드한 이미지는 로봇에서 안 돈다. buildx 로 멀티아키 빌드.
- 이미지 태그는 **불변**으로. `latest` 로 배포하면 무엇이 돌고 있는지 알 수 없다.
  git commit hash 를 태그에 넣는다.
- 컨테이너 안에서 DDS 가 통신하려면 네트워크 설정이 맞아야 한다.
  `network_mode: host` 가 가장 단순하지만 격리를 포기하는 것이다.
  분리하려면 멀티캐스트와 포트를 명시적으로 열어야 한다.
- 디바이스 접근(`/dev/ttyUSB*`, GPU, 카메라)은 `--device` 또는 udev 규칙으로 명시한다.
  `--privileged` 는 마지막 수단이다.

## 오케스트레이션 — 정말 필요한가부터

| 규모·상황 | 권장 |
|---|---|
| 로봇 온보드 프로세스 관리 | **systemd** (K8s 가 아니다) |
| 로봇 여러 대 + 현장 서버 | K3s / 경량 K8s, 또는 단순 Ansible |
| 클라우드 백엔드 (관제·대시보드) | Kubernetes |

**로봇 온보드에 Kubernetes 를 올리는 것은 대개 과설계다.**
온보드는 systemd 로 충분하고 더 안정적이다. K8s 는 서버 쪽에서 가치가 있다.
`robot-bringup` 스킬에 systemd 부팅 시퀀스 구성이 있다.

온보드 systemd 설계 요점:
- 의존 순서를 `After=`/`Requires=` 로 명시 (드라이버 → 상태추정 → 네비게이션)
- `Restart=on-failure` + `RestartSec` — 단, **무한 재시작 루프를 감지**해 알린다
- `WatchdogSec` 으로 헬스체크
- 로그는 journald 로 모으고 회전(rotation) 정책을 설정한다 — 디스크 채우면 로봇이 멈춘다

## OTA 업데이트

**현장 로봇 업데이트는 되돌릴 수 없으면 안 된다.**

- **A/B 파티션** 또는 이미지 태그 기반 롤백. 새 버전이 부팅 실패하면 자동으로 이전으로.
- 업데이트 조건을 정한다: 배터리 충분, 정지 상태, 작업 없음, 도킹 중.
  **주행 중 업데이트가 시작되면 안 된다.**
- 단계적 배포(카나리): 1대 → 몇 대 → 전체. 전체 동시 배포는 전 플릿을 한 번에 멈출 수 있다.
- 업데이트 후 **자동 검증**을 돌린다: 노드가 다 떴는가, 센서가 나오는가, TF 가 연결됐는가.
  실패하면 자동 롤백.
- 네트워크가 끊겨도 안전하게: 다운로드 완료 후 검증(체크섬) → 그다음 적용.
- 설정·캘리브레이션은 이미지와 **분리**한다. 업데이트가 개체별 캘리브레이션을 날리면 안 된다.

## 설정 · 시크릿 관리

- 로봇 개체별로 다른 것: 캘리브레이션, 로봇 ID, 네트워크, 하드웨어 옵션.
  이것을 이미지에 굽지 않는다. 마운트되는 설정 볼륨 또는 설정 서버에서 받는다.
- 시크릿(관제 인증, 클라우드 키)을 이미지·git 에 넣지 않는다.
  로봇마다 다른 자격증명을 쓰고 폐기·회전이 가능해야 한다.
- 설정 변경도 버전 관리한다. "누가 언제 이 파라미터를 바꿨는가" 가 사고 분석의 시작점이다.

## 모니터링 · 텔레메트리

수집할 최소 항목:

| 범주 | 지표 |
|---|---|
| 시스템 | CPU/코어별, 메모리, 디스크 여유, 온도, 전력 |
| ROS | 노드 생존, 주요 토픽 주기, `/diagnostics` |
| 로봇 상태 | 모드, 배터리, 주행거리, 오류 코드 |
| 작업 | 작업 성공/실패, 개입 횟수, 재계획 횟수 |
| 네트워크 | 연결 상태, 지연, 업로드 큐 |

- **개입 횟수(interventions)** 가 현장 품질의 가장 좋은 단일 지표다. 반드시 센다.
- 지표 수집이 로봇 성능을 갉아먹지 않게 주기와 양을 제한한다.
- 알림은 **행동 가능한 것만**. 알림이 많아지면 아무도 안 본다.
- 로그는 구조화(JSON)해서 보내고 로봇 ID·버전·세션 ID 를 항상 붙인다.

## 원격 진단

- 현장 로봇에 직접 SSH 하는 것을 기본 전략으로 삼지 않는다. 방화벽·NAT 뒤에 있다.
  역방향 터널(Tailscale/ZeroTier/WireGuard) 또는 관제 경유 명령 채널을 설계한다.
- **원격에서 무엇을 할 수 있고 무엇을 못 하는지 명시**한다.
  원격으로 로봇을 움직이는 기능은 안전 검토 대상이다.
- 문제 발생 시 자동으로 진단 번들(로그, 파라미터, 최근 bag 구간, 시스템 상태)을
  수집해 업로드하는 명령을 만들어 둔다. 현장 담당자에게 "로그 좀 보내주세요" 라고
  설명하는 비용이 사라진다.

## 납품 (commissioning)

현장 투입 절차를 체크리스트로 고정한다:

- [ ] 하드웨어 점검 (센서 장착, 배선, E-stop 동작 확인)
- [ ] 캘리브레이션 수행 및 결과 저장 (`robot-calibration`)
- [ ] 맵 생성 및 검증, 웨이포인트 등록
- [ ] 네트워크 구성 (WiFi 로밍, 관제 연결, 도메인 ID 충돌 확인)
- [ ] 안전 기능 실동 시험 (E-stop, 장애물 정지, 속도 제한)
- [ ] 시나리오별 주행/작업 시험 및 성공률 기록
- [ ] 8시간 연속 운용 시험
- [ ] 운영자 교육 및 매뉴얼 인계
- [ ] 지원 연락 체계·SLA 합의
- [ ] 인수 시험(FAT/SAT) 서명

**다중 로봇 현장이면 `ROS_DOMAIN_ID` 충돌과 DDS 디스커버리 폭주를 반드시 확인한다.**
같은 네트워크에 로봇 여러 대가 기본 도메인으로 뜨면 서로의 토픽을 구독한다.
`ros2-engineering/references/multi-robot.md` 참고.

## 유지보수

- 정기 점검 주기를 정의한다: 캘리브레이션 재확인, 센서 청소, 디스크 정리, 로그 회전 확인.
- **소모품 수명을 추적**한다 (배터리 사이클, 바퀴, 벨트, 그리퍼 패드).
  고장 후 대응이 아니라 예방 교체가 가동률을 지킨다.
- 장애 이력을 구조화해 쌓는다. 같은 고장이 반복되면 설계 문제지 운영 문제가 아니다.
- 고객사 담당자가 스스로 할 수 있는 1차 조치(재부팅, 도킹, 맵 재로드)를 문서화한다.
