# ELI5 — 쉬운 말로 처음부터

**쉽게 쓴다 = 정확도를 깎는다가 아니다.** 틀린 단순화는 설명이 아니라 오해를 심는 것이다.
쉬운 설명은 *같은 사실을 더 적은 사전지식으로* 전달한다.

이 스킬은 **어떤 문장을 쓸지**가 아니라 **무엇을 빠뜨리면 안 되는지**를 다룬다.

## 기본 뼈대

시간순으로 나열하지 않는다. 그건 로그지 설명이 아니다. 아래 다섯 칸을 채운다.

| 칸 | 답해야 하는 것 | 빠지면 생기는 일 |
|---|---|---|
| **왜 시작했나** | 원래 무엇이 안 됐나. 누구의 어떤 불편인가 | 뒤의 모든 결정이 근거 없이 보인다 |
| **뭘 만들어야 했나** | 목표 상태. 제약(시간·비용·안전) | "왜 이렇게 복잡하게 했어?" 가 남는다 |
| **뭐가 문제였나** | 예상 못 한 것. **여기가 설명의 핵심이다** | 쉬웠던 일처럼 들린다 |
| **어떻게 풀고 있나** | 대응. 왜 그 방법인지 | 대책이 임의로 보인다 |
| **뭐가 남았나** | 미해결·미검증·사람이 해야 하는 것 | 끝난 줄 안다 — **가장 위험한 오해** |

**"뭐가 문제였나" 에 가장 많은 분량을 쓴다.** 나머지는 요약해도 되지만 여기를 요약하면
설명이 "잘 돼 가고 있습니다" 로 뭉개진다.

## 원칙

- **용어를 번역하지 않는다. 처음 나올 때 한 번 풀어 준다.**
  `busy` → "움직이는 중이라는 표시(busy)" 로 한 번 쓰고, 그다음부터는 `busy`.
  번역해 버리면 사용자가 로그·문서·검색에서 그 단어를 못 찾는다.
- **숫자로 말한다.** "느리다" 가 아니라 "90 Hz 로 보내는데 0.67 Hz 밖에 못 받는다".
  숫자가 있으면 설명이 짧아지고, 틀렸을 때 상대가 지적할 수 있다.
- **검증 안 된 것은 검증 안 됐다고 말한다.** "테스트 266개 통과" 와 "실기에서 된다" 는
  다른 말이다. 쉬운 설명일수록 이 구분이 뭉개지기 쉽다.
- **어려운 부분을 건너뛰지 않는다.** 건너뛰고 싶은 그 부분이 설명이 필요한 곳이다.
  어려우면 은유를 쓰되 **은유의 한계를 같이 말한다** ("여기까지가 이 비유가 맞는 데까지다").
- **청자를 낮춰 보지 않는다.** "쉽게" 는 톤이 아니라 구조다. 감탄사·이모지·과장을 넣는 게
  아니라, 전제를 줄이고 순서를 바로잡는 것이다.

## 자주 나오는 실패

| 실패 | 증상 | 고치는 법 |
|---|---|---|
| 시간순 나열 | "9월 14일에 …, 9월 15일에 …" | 다섯 칸으로 재배치. 날짜는 근거로만 |
| 결론 없는 요약 | 읽고 나서 "그래서 되는 거야?" | 각 절 끝에 판정 한 줄 |
| 은유 과속 | 비유가 사실과 어긋나기 시작 | 비유는 한 문단까지. 넘으면 실제 용어로 |
| 성취 나열 | 한 일 목록만 있고 문제가 없다 | 막혔던 것·틀렸던 것을 먼저 쓴다 |
| 미검증을 검증된 것처럼 | "동작 확인했습니다" (가짜 기기에서) | 무엇으로 확인했는지 명시 |
| 남은 일 누락 | 끝난 것처럼 들림 | 마지막 칸을 비우지 않는다 |

## 로봇 작업에서 특히

- **실기와 시뮬을 문장마다 구분한다.** "돌아간다" 가 시뮬인지 실기인지 모르면 설명이 아니라
  위험 요소다. 가짜 기기·리플레이로 확인한 것은 그렇게 쓴다.
- **안전은 축약하지 않는다.** 소프트웨어 방어가 안전 기능이 아닌 경우(프로세스가 죽으면
  무력화되는 것), 그걸 쉬운 설명에서 빼면 상대는 안전하다고 이해한다. **여기서는 길어져도 된다.**
- **단위·좌표계·부호를 그대로 쓴다.** mm/m, rad/deg, 어느 frame 기준인지.
- 하드웨어가 아직 없으면 **"무엇이 가정이고 무엇이 확인된 것인지"** 를 분리해 적는다.

## 청자에 따라 조절

| 청자 | 더 넣을 것 | 뺄 것 |
|---|---|---|
| 같은 팀 개발자 | 파일·함수 이름, 재현 명령 | 도메인 배경 |
| 다른 팀·관리자 | 왜 오래 걸리는지, 리스크와 일정 영향 | 코드 구조 |
| 인수인계 받는 사람 | 함정, "여기서 내가 틀렸었다", 시작점 문서 | 이미 해결된 과정의 세부 |
| 고객·비전문가 | 무엇이 보장되고 무엇이 안 되는지 | 내부 구조 전체 |

## 길이와 형식

- 기본은 **다섯 칸 구조 + 표**. 줄글로만 쓰면 다시 찾아보기 어렵다.
- 비교·선택지는 표로. 시간 흐름이 정말 필요하면 그때만 순서대로.
- 한 절이 화면을 넘기면 표로 바꿀 수 있는지 본다.
- 마지막에 **"한 가지만 기억한다면"** 한 문단. 여기에는 보통 *가장 흔한 오해*를 적는다.

## 끝내기 전 확인

- [ ] 다섯 칸이 다 찼는가 (특히 **문제**와 **남은 것**)
- [ ] 검증된 것과 안 된 것이 문장 단위로 구분되는가
- [ ] 실기/시뮬이 구분되는가
- [ ] 용어를 번역해 버려서 검색이 안 되게 만들지 않았는가
- [ ] 상대가 **다음에 무엇을 해야 하는지** 알 수 있는가
