# GPU 최적화 (온보드 추론)

로봇의 GPU 는 데이터센터 GPU 가 아니다. **전력·열·메모리가 전부 제약**이고,
지연의 분산(p99)이 평균보다 중요하다.

## 최적화 순서 — 효과 큰 것부터

1. **입력 크기 줄이기** — 해상도, 포인트 수, 배치. 가장 효과가 크고 가장 자주 간과된다.
   1080p → 720p 만으로 절반 이하가 되는 경우가 흔하다.
2. **런타임 변환** — PyTorch 직접 실행 → TensorRT/ONNX Runtime. 보통 2~5배.
3. **정밀도 낮추기** — FP32 → FP16 → INT8.
4. **파이프라인 정리** — 전처리/후처리/복사 제거. 여기가 병목인 경우가 매우 많다.
5. **모델 구조 변경** — 경량 백본, 증류. 재학습이 필요해 비용이 크다.
6. **커널 최적화** — 직접 CUDA 작성. 마지막 수단.

## 측정 — 끝단에서 재라

**모델 forward 시간만 재면 거의 항상 틀린 결론이 나온다.**

```
전체 지연 = 취득 → 전처리 → H2D 복사 → 추론 → D2H 복사 → 후처리 → 발행
```

- 각 구간을 개별 측정한다. 추론이 20 ms 인데 전처리가 40 ms 인 경우가 흔하다.
- CUDA 는 **비동기**다. `cudaEventRecord`/`cudaStreamSynchronize` 또는
  `torch.cuda.synchronize()` 없이 잰 시간은 거짓이다.
- **p50 이 아니라 p99 를 본다.** 제어 주기를 지키려면 최악값이 기준이다.
- 워밍업 후 측정한다. 첫 수십 회는 커널 컴파일/캐시 때문에 느리다.

도구: `nsys profile`(전체 타임라인), `ncu`(커널 상세), `tegrastats`(Jetson),
`nvidia-smi dmon`(사용률·전력·온도).

## TensorRT

```
PyTorch → ONNX export → trtexec 로 엔진 빌드 → 런타임 로드
```

- **엔진은 GPU·TensorRT 버전에 종속**이다. 빌드한 기기와 배포 기기가 다르면 안 된다.
  타깃 기기에서 빌드하거나 동일 환경 컨테이너를 쓴다. 현장 배포에서 자주 터지는 문제.
- 동적 shape 을 쓰면 최적화 프로파일(min/opt/max)을 명시한다.
  가능하면 **고정 shape** 이 가장 빠르다.
- `--fp16` 는 대개 정확도 손실이 거의 없다. 먼저 시도한다.
- `--int8` 은 캘리브레이션 데이터셋이 필요하다. 대표성 있는 실제 데이터를 쓴다.
  합성 데이터로 캘리브레이션하면 현장 정확도가 떨어진다.
- **정밀도를 낮춘 후 반드시 정확도를 재측정**한다. 검증 세트 성능이 얼마나 떨어졌는지
  숫자로 확인하지 않고 배포하지 않는다.
- 지원되지 않는 연산이 있으면 그 부분만 폴백되어 느려진다. 빌드 로그에서 확인한다.

## 메모리

- **VRAM 은 로봇에서 가장 빡빡한 자원**이다. 여러 모델을 동시에 올리면 금방 넘친다.
- 메모리 풀을 미리 할당하고 재사용한다. 추론 중 할당은 지연 스파이크를 만든다.
- Jetson 은 **통합 메모리(unified memory)** 다 — CPU/GPU 가 물리 메모리를 공유한다.
  따라서 `cudaHostAlloc`/pinned memory 나 zero-copy 로 **복사를 아예 없앨 수 있다.**
  dGPU 코드를 그대로 옮기면 불필요한 복사가 남는다.
- 여러 모델이 필요하면 순차 실행 + 언로드보다 **작은 모델 하나로 통합**을 먼저 검토한다.

## 파이프라인 설계

- **CPU↔GPU 왕복을 최소화**한다. 전처리·후처리도 GPU 에서 하면 왕복이 사라진다.
  (CUDA 로 리사이즈/정규화, NPP, CV-CUDA 등)
- ROS 2 에서는 노드 사이에 일반 노드가 끼면 GPU 메모리가 CPU 로 내려온다.
  Isaac ROS 의 NITROS 처럼 GPU 메모리를 유지하는 경로를 쓴다 (`nvidia-isaac` 스킬).
- **추론과 제어를 분리**한다. 추론은 별도 스레드/프로세스에서 돌고,
  제어 루프는 최신 결과를 논블로킹으로 읽는다. 추론이 늦어도 제어가 멈추면 안 된다.
- 여러 스트림(`cudaStream`)으로 전처리·추론·후처리를 겹치면 처리량이 오른다.
  단 지연 분산이 커질 수 있으니 실시간 요구가 있으면 신중히.

## 배치

- 로봇 실시간 추론은 대개 **배치 1** 이다. 배치를 키우면 처리량은 오르지만 지연이 는다.
- 카메라가 여러 대면 배치가 의미 있다 — 4대를 배치 4로 묶으면 4번 추론보다 빠르다.
  단 모든 카메라 프레임이 도착할 때까지 기다리는 지연이 추가된다. 트레이드오프를 계산한다.

## Jetson 특유

- **전력 모드를 고정**한다: `nvpmodel -m 0`(최대) 등. 모드가 다르면 성능이 배로 달라진다.
- `jetson_clocks` 로 클럭을 고정하지 않으면 벤치마크가 재현되지 않는다.
- 열 스로틀링을 반드시 확인한다. 장시간 구동 시 성능이 떨어진다 (`tegrastats` 로 온도 기록).
- DLA(딥러닝 가속기)가 있으면 일부 모델을 오프로드해 GPU 를 비울 수 있다.
  단 지원 연산이 제한적이다.
- 전력 예산이 로봇 배터리와 직결된다. 성능만 보고 최대 모드로 두면 가동 시간이 준다.

## 직접 CUDA 커널을 쓸 때

- 먼저 **기존 라이브러리로 되는지 확인**한다 (cuBLAS, cuDNN, Thrust, CUB, PCL-GPU, CV-CUDA).
  직접 짠 커널이 라이브러리보다 빠른 경우는 드물다.
- 병목이 연산인지 **메모리 대역폭**인지 먼저 판단한다 (`ncu` 의 roofline).
  대부분의 로봇 연산(포인트클라우드 처리)은 메모리 바운드다 — 연산 최적화는 효과가 없다.
- 메모리 접근을 coalesced 하게. warp divergence 를 줄인다.
- 커널 하나당 하는 일을 늘려 **커널 런치 횟수를 줄인다.** 런치 오버헤드가 무시 못 한다.

## 배포 전 체크리스트

- [ ] 타깃 기기에서 빌드/검증했는가 (엔진 호환성)
- [ ] p99 지연이 제어 주기 예산 안에 있는가
- [ ] 정밀도 변환 후 정확도를 재측정했는가
- [ ] 30분 이상 연속 구동 시 성능이 유지되는가 (열)
- [ ] VRAM 최대 사용량에 여유가 있는가
- [ ] 추론 실패/타임아웃 시 로봇 동작이 정의돼 있는가
