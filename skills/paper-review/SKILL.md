# 논문 리뷰

**요약이 아니다.** 요약은 `paper-summarize` 가 한다. 여기서 하는 일은
**"이 논문이 주장하는 것을 믿어도 되는가, 그리고 우리에게 무슨 의미인가"** 를 판정하는 것이다.

읽고 나서 아래 두 문장을 쓸 수 없으면 아직 리뷰가 안 끝난 것이다.
- 이 논문의 **핵심 주장 한 문장**과, 그것을 지탱하는 **증거 한 가지**
- 그 증거가 **무너지는 조건 한 가지**

## 읽는 순서 — 처음부터 순서대로 읽지 않는다

1. **초록 + 그림/표 먼저.** 저자가 무엇을 자랑하려는지, 어떤 숫자로 자랑하는지 먼저 본다
2. **실험 설정.** 방법보다 먼저 본다. 설정이 이상하면 방법을 읽을 이유가 없다
3. **방법.** 이제 "왜 이렇게 했는지" 가 읽힌다
4. **관련 연구.** 마지막에 본다 — 저자가 누구와 비교하기를 **피했는지** 가 보인다

## 비평 체크리스트

### 주장 대 증거
- 초록의 주장과 실험이 **같은 것을 말하는가.** "일반화된다" 고 써놓고 같은 분포에서만 평가하는 경우가 많다
- 개선폭이 **분산보다 큰가.** 시드 3개에 ±2%p 인데 1.5%p 개선이면 주장할 수 없다
- **시드 개수와 표준편차가 적혀 있는가.** 없으면 그 수치는 1회 측정치로 취급한다
- **ablation 이 있는가.** 없으면 어느 요소가 효과를 냈는지 저자도 모르는 것이다

### 베이스라인 공정성 — 여기서 가장 많이 속는다
- 베이스라인이 **같은 데이터·같은 튜닝 예산**을 받았는가. 자기 방법만 튜닝한 비교가 흔하다
- 베이스라인이 **원 논문 수치인가 재구현인가.** 재구현이면 대개 낮게 나온다
- 최신 강한 베이스라인이 **빠져 있지 않은가**

### 재현 가능성
- 코드·데이터·체크포인트·하이퍼파라미터가 **실제로 공개돼 있는가** (링크가 있는 것과 동작하는 것은 다르다)
- 학습 비용이 우리가 감당 가능한가 → 외장 GPU 가 없으므로 `cloud-gpu-job` 기준으로 환산한다
- 평가 코드가 공개됐는가. **학습 코드만 있고 평가 코드가 없으면 숫자를 검증할 수 없다**

### 로봇 논문 특유의 함정
- **시뮬만인가 실기가 있는가.** 실기가 있으면 **몇 회**인가. 10회 미만은 경향으로만 읽는다
- **성공률의 정의**가 무엇인가. 부분 성공을 성공으로 세는 경우가 있다
- **리셋 정책** — 매 시도마다 사람이 물체를 정확히 같은 자리에 놓았는가. 그러면 일반화 주장이 약해진다
- 영상이 **체리픽**인가. 실패 영상이 없으면 그렇게 가정한다
- 하드웨어 특수성 — 그 로봇에서만 되는 것은 아닌가 (그리퍼, 촉각, 카메라 배치)
- 제어 주기·지연이 명시됐는가. 온보드에서 못 돌리는 주기면 우리에겐 무의미하다

## 우리 작업과 연결 — 이게 빠지면 그냥 독후감이다

- **적용 대상**: G2(산업 매니퓰레이션) / X2(휴머노이드) / D1(4족) 중 어디에 해당하는가
- **필요한 것**: 데이터 몇 시간, GPU 얼마, 실기 접근 필요 여부
- **막는 것**: 우리 하드웨어·미들웨어(G2 는 Cosine/Aorta, X2 는 AimRT)와 안 맞는 지점
- **바로 쓸 수 있는 조각**: 전체를 안 가져와도 되는 부분 (손실함수, 데이터 증강, 평가 지표)
- 판정: **지금 시도 / 나중에 / 안 함** 중 하나를 반드시 적는다

## 여러 편을 볼 때 (스터디)

- **계보를 그린다.** A→B→C 로 무엇이 바뀌었고 무엇이 그대로인지
- 같은 벤치마크 수치는 **표로 모은다.** 논문마다 유리한 설정으로 보고하므로 설정 열을 함께 둔다
- **서로 모순되는 결과**를 찾는다. 거기가 아직 안 풀린 지점이고 우리가 낄 자리다
- 3편 이상 읽었으면 **"이 분야가 아직 못 하는 것"** 을 한 줄로 적는다

## 출력

```markdown
# <제목> (저자, 학회/arXiv, 연도)  링크

## 한 줄
주장 / 무엇으로 뒷받침 / 어디서 무너지는가

## 방법
(우리 용어로 다시 쓴다. 논문 표기를 그대로 옮기지 않는다)

## 증거 평가
| 항목 | 확인 | 근거 |
|---|---|---|
| 시드·분산 명시 | ✅/⚠️/❌ | |
| 베이스라인 공정성 | | |
| ablation | | |
| 실기 검증 (횟수) | | |
| 코드·평가코드 공개 | | |

## 한계 — 저자가 쓴 것 + 저자가 안 쓴 것
## 우리 적용: 대상 / 필요 자원 / 막는 것 / 판정(지금·나중·안함)
## 관련: [[다른 리뷰 파일]]
```

저장: `~/knowledge/papers/reviews/YYYYMMDD-<슬러그>.md`
(수집물은 `~/knowledge/papers/<카테고리>/` 에 따로 쌓인다 — 섞지 않는다)

## Gotchas

- **읽지 않은 부분을 읽은 것처럼 쓰지 않는다.** PDF 를 못 열었으면 "초록만 봄" 이라고 명시한다
- 저자의 요약을 그대로 옮기지 않는다. 그건 `paper-summarize` 가 이미 한다
- 수치를 인용할 때 **어느 표·어느 설정인지** 함께 적는다
- 부정적 평가를 흐리지 않는다. "흥미롭다" 로 끝나는 리뷰는 쓸모가 없다
- 우리 프로젝트 적용 판단에서 **시뮬 결과와 실기 결과를 섞지 않는다**
